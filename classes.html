Classes & Access Specifiers 🔐

Who can touch what — the bouncer system of C++, plus the scope resolution operator and the mysterious this pointer.

1 Anatomy of a class — our lab specimen 🔬

We'll dissect this one program for the whole note. Read it once; every section below explains a piece of it.

#include <iostream>
using namespace std;

class emp {
private:
    int a, b, c;                    // hidden — VIP room
public:
    int d, e;                       // open to all
    void setData(int a, int b, int c);  // declared only
    void getData() {                // defined inside class
        cout << a << b << c << d << e;
    }
};

// defined OUTSIDE the class using :: 
void emp :: setData(int a, int b, int c) {
    this->a = a;
    this->b = b;
    this->c = c;
}

int main() {
    emp affan;             // object born — memory allocated
    affan.setData(9,8,8);  // ✅ public method → sets private a,b,c
    affan.d = 9;           // ✅ d is public — direct access OK
    affan.e = 7;           // ✅ e is public too
    affan.getData();       // prints everything
    // affan.a = 5;        // ❌ COMPILE ERROR — a is private!
    return 0;
}
  • The class mixes private data (a,b,c) and public data (d,e) deliberately — so you can feel the difference.
  • Private members aren't unreachable — they're reachable only through public methods (setData/getData). The methods are the official doorway.

2 The 3 access specifiers — the nightclub model 🎟️

Accessible from…private 🔴protected 🟡public 🟢
Inside the same class (member functions)✓✓✓
Derived (child) class✗✓✓
Outside (e.g. main(), via object)✗✗✓
  • Access is checked at compile time — affan.a = 5; won't even build. The bouncer works before the party starts.
  • Default access in a class is private. Write no specifier → everything is locked.
  • protected = private + one exception: children (derived classes) inherit the key. It only matters once inheritance enters (Note on inheritance later).
💡 Memory hook: 🔴 private = vault (staff only) · 🟡 protected = family lounge (family/children allowed) · 🟢 public = dance floor (everyone welcome). The compiler is the bouncer — it stops you at the door (compile time), not inside the club (runtime).
🎯 Interview lines:
① "Private members are inaccessible outside the class — attempting it gives a compile-time error, since C++ enforces access control at compilation."
② "The only difference between class and struct is default access: class → private, struct → public."

3 Why keep data private at all? (getter/setter pattern)

  • If a were public, any code anywhere could set it to garbage (affan.a = -99999;) — and you'd never know who did it.
  • A setter is a checkpoint: it can validate before accepting a value. A getter exposes the value read-only.
  • This is encapsulation in action — not hiding for secrecy, but controlled access.
void setSalary(int s) {
    if (s >= 0)          // the checkpoint 🛂
        salary = s;      // only sane values get in
}
💡 Memory hook: setter = airport security 🛂 — everyone passes through the scanner; no direct jumping onto the plane (the variable).

4 The :: scope resolution operator

  • Inside the class we only declared setData; we defined it outside using void emp :: setData(...).
  • emp :: tells the compiler: "this function belongs to class emp" — its full address, not just its name.
  • Why define outside? Keeps the class body short and readable (like a table of contents), with implementations elsewhere — the standard style in real projects (declarations in .h files, definitions in .cpp files).
💡 Memory hook: emp::setData reads like a home address — "setData, resident of house emp". :: = "belongs to".

5 The this pointer — "I mean MY variable"

Look at the name clash in our code: the parameters are named a, b, c and the data members are also a, b, c. Inside the function, plain a means the nearest one — the parameter. So how do we reach the member?

void emp :: setData(int a, int b, int c) {
    this->a = a;   // MY a  =  parameter a
    this->b = b;   // this → the object that called me
    this->c = c;
}
  • this is a hidden pointer every (non-static) member function receives automatically — it points to the object that called the function.
  • When affan.setData(9,8,8) runs, this = &affan. If rahul.setData(...) ran, this = &rahul. Same function code, different this.
  • This is also how one copy of a function serves all objects: data members exist per-object, but member functions exist once, and this tells them whose data to work on.
  • Without a name clash, this-> is optional — the compiler adds it silently. With a clash, it's mandatory.
💡 Memory hook: this = the word "my". this->a literally reads as "my a", versus the visitor a that walked in through the parameter door.
🎯 Interview line: "this is an implicit pointer passed to every non-static member function, holding the address of the invoking object. It resolves naming conflicts between parameters and data members, and enables method chaining by returning *this."

⚠️ Design note: our specimen makes d,e public just to demonstrate — in real code, data members should almost always be private and reached via methods. Public data = back to procedural chaos (Note 01!).

★ 30-second revision

  • 🔴 private = vault (class only, the default) · 🟡 protected = family lounge (+ children) · 🟢 public = dance floor (everyone)
  • Access control is enforced by the compiler (compile-time errors) — the bouncer at the door
  • emp :: setData — :: = "belongs to"; declare inside, define outside
  • this = hidden pointer to the calling object = the word "my"; mandatory when parameter names shadow member names
  • One function copy serves all objects — this tells it whose data to touch
  • Real code: data private, interface public. Always.
