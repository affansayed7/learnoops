Polymorphism 🎭

Many forms, one interface — compile-time overloading, runtime virtual dispatch, the vtable underneath it, and the two mistakes that leak memory or silently lose data.

1 Compile-time vs runtime polymorphism

Polymorphism: "many forms" — the same interface (function name, operator) producing different behavior depending on type or context.
Compile-time (static)Runtime (dynamic)
Achieved byFunction overloading, operator overloading, templatesVirtual functions through a base pointer/reference
ResolvedAt compilation (early binding)At execution (late binding)
MechanismSignature matchingvtable + vptr lookup
CostZero — fully inlinableOne indirection; usually blocks inlining
💡 Hook: Compile-time = choosing from a fixed menu 📋 before arriving. Runtime = the chef's surprise 🍽️ — decided when the dish actually arrives.

2 Runtime polymorphism in action

class Shape {
public:
    virtual void draw() { cout << "Shape\n"; }
    virtual ~Shape() = default;
};
class Circle : public Shape {
public:
    void draw() override { cout << "Circle\n"; }
};
class Square : public Shape {
public:
    void draw() override { cout << "Square\n"; }
};
void render(Shape* s) { s->draw(); }   // doesn't know or care which subtype

int main() {
    Circle c; Square sq;
    render(&c);    // "Circle"
    render(&sq);   // "Square" — SAME call, different behavior
}
🎯 Interview line: "Runtime polymorphism means the same call site (`s->draw()`) dispatches differently depending on the object's actual dynamic type, decided at runtime through the vtable."

3 Overriding vs Overloading vs Hiding — the final word

virtual needed?NoYes (in base)No
BindingCompile-timeRuntimeCompile-time
⚠️ Without virtual, calling a same-signature function through a base pointer is static binding — it always calls the BASE version, regardless of the actual object type:
class Base {
public:
    void speak() { cout << "Base\n"; }   // NOT virtual
};
class Derived : public Base {
public:
    void speak() { cout << "Derived\n"; }
};
Base* p = new Derived();
p->speak();   // prints "Base" — no virtual, no dispatch, decided at compile time by pointer TYPE
💡 Always write override — if your signature doesn't actually match a virtual base function, the compiler errors instead of silently creating an unrelated new function.

4 The vtable/vptr mechanism

  • Any class with ≥1 virtual function gets a vtable: one array of function pointers, shared by the whole class.
  • Every object of that class carries a hidden vptr pointing to its class's vtable — this is why sizeof grows (typically +8 bytes on 64-bit) the moment a class gains its first virtual function.
  • A call p->draw() compiles to: follow vptr → index into vtable → call that address. One indirection.
  • The vptr is set up during construction — which is exactly why constructors can never be virtual, and why calling a virtual function inside a constructor resolves to the base version (the derived vptr isn't wired up yet).
💡 Hook: vtable = a restaurant's menu (one per restaurant/class). vptr = the menu in your hand (one per customer/object). Say "item #1" — what arrives depends on which menu you're holding.

5 Virtual destructors — the leak everyone eventually causes

class Base {
public:
    ~Base() { cout << "~Base\n"; }        // ❌ NOT virtual
};
class Derived : public Base {
    int* data;
public:
    Derived()  { data = new int[1000]; }
    ~Derived() { delete[] data; cout << "~Derived\n"; }
};
Base* p = new Derived();
delete p;   // UNDEFINED BEHAVIOR — typically only "~Base" prints, Derived's dtor is skipped, 4000 bytes leak

// FIX — one keyword:
class Base {
public: virtual ~Base() { cout << "~Base\n"; }
};
// now: "~Derived" then "~Base" — correct, via the vtable, reverse order
⚠️ Deleting a derived object through a base pointer with a non-virtual destructor is technically undefined behavior — in practice, most compilers simply skip the derived destructor, silently leaking whatever it owned.
🎯 Interview line: "Any class meant to be used polymorphically — deleted through a base pointer — needs a virtual destructor. Without it, only the base's destructor runs, and the derived part's resources leak."
💡 Hook: ☠️ A non-virtual destructor is a demolition crew that only tears down the ground floor, leaving everything the derived class built standing in memory forever.

6 Pure virtual functions & abstract classes

Pure virtual function: virtual void draw() = 0; — derived classes must override it.
Abstract class: any class with ≥1 pure virtual function. Cannot be instantiated directly.
class Shape {
public:
    virtual double area() const = 0;     // pure virtual
    virtual ~Shape() = default;
};
// Shape s;               // ❌ error: cannot instantiate abstract class
class Circle : public Shape {
    double r;
public:
    Circle(double r) : r(r) {}
    double area() const override { return 3.14159 * r * r; }
};
Shape* s = new Circle(2);
cout << s->area();   // 12.566...
delete s;
  • A derived class that doesn't override every pure virtual function is itself still abstract.
  • Surprising but true: a pure virtual function can have a body — useful as a shared default that derived classes call explicitly via Base::func(). = 0 only means "must be overridden," not "has no implementation."
  • C++ has no interface keyword — the pattern is an abstract class with only pure virtuals and no data.
🎯 Interview line: "An abstract class defines a contract via pure virtual functions and can't be instantiated — but a pointer or reference to it is exactly how polymorphism works: hold any concrete subtype behind one interface."

7 Object slicing 🔪

Slicing: assigning or passing a derived object by value to a base-typed variable discards the derived part — only the base subobject survives, and polymorphism is lost.
class Base { public: virtual void id() { cout << "Base\n"; } };
class Derived : public Base {
    int extra = 42;
public: void id() override { cout << "Derived\n"; }
};

void byValue(Base b)  { b.id(); }    // 🔪 SLICED → "Base"
void byRef(Base& b)   { b.id(); }    // ✅ polymorphic → "Derived"

Derived d;
byValue(d);    // "Base"    — the trap
byRef(d);      // "Derived"
Base b2 = d;   // 🔪 sliced: extra discarded, b2's vptr is Base's
⚠️ It compiles without warning. vector<Base> holding "derived" objects slices every single one on insertion. Fix: store vector<unique_ptr<Base>> instead, and always pass polymorphic types by reference or pointer.
💡 Hook: 🔪 Forcing a tall person into a short box — you keep what fits, and nobody warns you what got cut off.

★ 30-second revision

  • Compile-time poly: overloading/templates, zero cost. Runtime poly: virtual functions, one indirection via vtable/vptr.
  • No virtual + same signature in derived → hiding, static binding, always calls base through a base pointer.
  • vptr set up during construction → constructors can't be virtual, virtual calls in ctors resolve to base.
  • Polymorphic base classes → always need a virtual destructor, or deleting through the base leaks.
  • Pure virtual (=0) → class is abstract, can't instantiate. It CAN still have a body.
  • Object slicing: passing/assigning derived objects by value to base types discards the derived part — always use reference/pointer for polymorphic types.
