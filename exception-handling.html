Exception Handling 🛡️

Object slicing comes back to haunt catch blocks, RAII pays off exactly when things go wrong, and one dropped keyword can crash your whole program.

1 The basics: try, throw, catch

try {
    if (balance < amt)
        throw std::runtime_error("insufficient funds");
    balance -= amt;
} catch (const std::runtime_error& e) {
    cout << "Caught: " << e.what();
}
  • throw creates an exception object and immediately starts unwinding the stack, looking for a matching catch.
  • e.what() returns a human-readable message — it's a virtual function defined on std::exception and overridden by its derived types.

2 Custom exception classes

class InsufficientFundsException : public std::runtime_error {
public:
    InsufficientFundsException(double shortfall)
        : std::runtime_error("Insufficient funds, short by " + std::to_string(shortfall)) {}
};

void withdraw(double balance, double amt) {
    if (amt > balance)
        throw InsufficientFundsException(amt - balance);
}
try { withdraw(100, 150); }
catch (const InsufficientFundsException& e) { cout << e.what(); }
💡 Standard practice: derive custom exceptions from std::runtime_error or std::exception, and pass your message to the base constructor — you get what() for free.

3 Catch by reference, not by value — slicing strikes again

try {
    throw std::runtime_error("disk full");
} catch (std::exception e) {          // ❌ caught BY VALUE — sliced!
    cout << e.what();                  // prints a GENERIC message, NOT "disk full"
}
// -----------------------------------------------------------
try {
    throw std::runtime_error("disk full");
} catch (const std::exception& e) {   // ✅ caught by reference — polymorphism preserved
    cout << e.what();                       // prints "disk full"
}
⚠️ Catching std::exception e by value slices the thrown runtime_error down to a plain std::exception — same object-slicing bug from the Polymorphism note, now in a catch block. The sliced copy's vtable points to std::exception, so e.what() calls the base's generic version, not runtime_error's stored message.
🎯 Interview line: "I always catch by const reference. Catching by value slices the exception object and can silently discard both its derived type and its actual message."

4 Catch block order — most-derived first

try {
    throw std::runtime_error("oops");
}
catch (std::exception& e)       { cout << "exception"; }      // ❌ matches FIRST — too general
catch (std::runtime_error& e)  { cout << "runtime_error"; } // unreachable! never runs
  • Catch blocks are tried top to bottom, first match wins. Since runtime_error IS-A exception, the general catch above matches everything, making the specific one below dead code.
  • Fix: order from most specific to most general — derived classes' catch blocks first, base class (or catch(...)) last as a fallback.
catch (std::runtime_error& e) { ... }   // specific — checked first
catch (std::exception& e)  { ... }   // general fallback — checked last
catch (...)                { ... }   // catches literally anything, even non-exception types

5 Stack unwinding & RAII — where it all pays off

  • When an exception propagates, the stack unwinds — every local object between the throw and the matching catch has its destructor called, in reverse order of construction.
  • This is exactly why RAII (Note 06) matters: a lock_guard or unique_ptr releases its resource automatically during unwinding, even though no code explicitly told it to.
void process() {
    std::lock_guard<std::mutex> lock(mtx);   // acquires the mutex
    riskyOperation();                        // throws!
    // lock_guard's destructor STILL runs during unwinding → mutex released, no deadlock
}
🎯 Interview line: "Stack unwinding guarantees destructors run even when an exception propagates — that's what makes RAII exception-safe without needing a `finally` block."

6 noexcept and rethrowing

void safeFunc() noexcept {
    throw std::runtime_error("oops");   // std::terminate() is called IMMEDIATELY — not caught, even by an outer try/catch
}
⚠️ A function marked noexcept that throws anyway causes an instant program termination via std::terminate() — the exception does not propagate normally, and no catch block anywhere can intercept it.
try {
    doSomething();
} catch (const std::exception& e) {
    log(e.what());
    throw;        // ✅ re-throws the SAME exception, preserving its original dynamic type
    // throw e;   ❌ would COPY-CONSTRUCT a new exception from e's STATIC type — can re-introduce slicing
}
💡 Hook: bare throw; = "hand the same letter back." throw e; = "write a new letter based on what you can currently see of the old one" — and if e is a base reference, that new letter is a sliced copy.

7 Exception safety guarantees

GuaranteeMeaning
BasicNo leaks; object remains in some valid (but possibly changed) state
StrongCommit-or-rollback — the operation either fully succeeds or the object is left completely unchanged
Nothrow (noexcept)Guaranteed to never throw at all
💡 std::vector::push_back gives the strong guarantee: if the reallocation fails partway through, the vector is left exactly as it was before the call. RAII is how this is achieved for free.

★ 30-second revision

  • Always catch by const& — catching by value slices the exception and can silently change what what() returns
  • Order catch blocks derived → base; a base catch placed first makes every derived catch below it unreachable
  • Custom exceptions inherit from std::runtime_error/std::exception, passing the message to the base constructor
  • Stack unwinding runs destructors in reverse order → this is why RAII makes code exception-safe
  • A noexcept function that throws → std::terminate() immediately, no catch can intercept it
  • Bare throw; rethrows the original exception intact. throw e; copies from e's static type — can slice
  • Three safety levels: basic (no leak), strong (commit-or-rollback), nothrow
