Constructors & Destructors — Full Depth 👶👋

Every type of constructor, the initializer-list trap that catches almost everyone once, and exactly when destruction happens.

1 Quick recap, then we go deep

  • A constructor is a special member function that runs automatically when an object is created — same name as the class, no return type (not even void).
  • Its job: put the object into a valid initial state before anyone can use it.
  • C++ gives you four kinds: default, parameterized, copy, and move. We'll build each one on the same class.

2 The four constructors

class Point {
    int x, y;
public:
    Point()                          // ① DEFAULT — no arguments
        : x(0), y(0) {}

    Point(int a, int b)             // ② PARAMETERIZED
        : x(a), y(b) {}

    Point(const Point& other)      // ③ COPY — takes a const reference
        : x(other.x), y(other.y) {}

    Point(Point&& other) noexcept       // ④ MOVE — takes an rvalue reference (C++11)
        : x(other.x), y(other.y) {}
};
TypeCalled when
DefaultPoint p; — no arguments given
ParameterizedPoint p(3, 4);
CopyPoint p2 = p1; · passing by value · returning by value
MoveSource is a temporary/rvalue, or explicitly std::move(p1)
⚠️ Full move-semantics mechanics (why it matters, what "stealing" a resource means) belongs to the Copy Semantics / Rule of Three-Five-Zero note later — here, just know it exists and when it's picked.
💡 Memory hook: Default = a blank form 📄. Parameterized = a filled-in form ✍️. Copy = a photocopy 📠. Move = handing over the original and keeping nothing 🤝.

3 The trap: = doesn't always mean assignment

This single line confuses almost everyone the first time:

Point p1(3, 4);
Point p2 = p1;     // looks like assignment... but it's NOT
p2 = p1;           // THIS is assignment
  • Point p2 = p1; is copy-initialization — p2 doesn't exist yet, so this calls the copy constructor. The = here is just initialization syntax, not the assignment operator.
  • p2 = p1; (on its own line, p2 already exists) calls operator= — the copy assignment operator — a completely different function.
⚠️ Rule of thumb: if the variable is being declared on that line, it's construction (copy constructor). If it already exists, it's assignment. Same symbol =, two different functions.
🎯 Interview line: "`T b = a;` is copy-initialization and invokes the copy constructor, not `operator=`, because `b` is being created, not reassigned. `operator=` only fires when the target object already exists."

4 The member initializer list

  • : x(a), y(b) — this is initialization, not assignment. Members get their value the moment they're born.
  • Writing it in the body instead — { x = a; y = b; } — first default-constructs the members, then overwrites them. Wasteful for non-trivial types, and sometimes not even legal (see below).
  • Mandatory for: const members, reference members, and members/base classes with no default constructor — none of these can be assigned to after the fact.
class Config {
    const int id;      // const — MUST be initialized, can't be assigned later
    int& ref;         // reference — same rule
public:
    Config(int i, int& r) : id(i), ref(r) {}   // ✅ only way that compiles
    // Config(int i, int& r) { id = i; ref = r; }  // ❌ won't compile
};

⚠️ The trap nobody sees coming: initialization order

Members are initialized in the order they're declared in the class — NOT the order you write them in the initializer list.

class Broken {
    int a;    // declared FIRST → initialized FIRST
    int b;    // declared SECOND → initialized SECOND
public:
    Broken(int x) : b(x), a(b) {}   // looks like: set b, then a=b
    // ACTUAL execution order: a(b) runs FIRST — but b isn't set yet!
    // a gets garbage. Then b(x) runs. a != b, silently wrong.
};
⚠️ Most compilers warn about this (-Wreorder) — but it still compiles and runs with a silently wrong value. Always write the initializer list in declaration order to avoid confusing yourself, even though the compiler ignores your written order anyway.
💡 Memory hook: The initializer list is not a to-do list read top to bottom — the class's own declaration order is the real schedule. The list is just where you write each item's value.
🎯 Interview line: "Members initialize in declaration order regardless of initializer-list order — a classic bug appears when one member's initializer depends on another member declared later in the class."

5 The default constructor disappears the moment you write any other

class Point {
    int x, y;
public:
    Point(int a, int b) : x(a), y(b) {}   // you wrote ONE constructor
};

Point p;         // ❌ COMPILE ERROR — no default constructor exists!
Point p2(1, 2);  // ✅ fine
  • The compiler only auto-generates a default constructor if you define zero constructors yourself.
  • The instant you write any constructor — even just a copy constructor — the free default constructor is gone.
  • Want it back anyway? Ask explicitly (C++11): Point() = default;
⚠️ This is one of the single most common "why won't my code compile" moments for people learning C++. If you see "no matching function for call to 'X::X()'", check whether you defined any other constructor.

6 Delegating constructors (C++11) — avoid repeating yourself

class Box {
    int w, h;
public:
    Box(int w, int h) : w(w), h(h) {}
    Box() : Box(1, 1) {}          // delegates — calls the constructor above
    Box(int side) : Box(side, side) {}  // also delegates
};
  • One constructor can call another constructor of the same class from its initializer list — avoiding duplicated setup logic.
  • Rule: if a constructor delegates, that's the only thing allowed in its initializer list — you can't delegate AND initialize other members in the same list.
💡 Memory hook: Delegating = forwarding a call ☎️ to a colleague who already knows how to handle it, instead of explaining the whole thing again yourself.

7 explicit — stopping silent conversions

class Wrapper {
public:
    Wrapper(int x) {}          // single-argument constructor
};

void process(Wrapper w) {}

process(5);              // ⚠️ compiles! 5 is silently converted to Wrapper(5)

class SafeWrapper {
public:
    explicit SafeWrapper(int x) {}
};

void process2(SafeWrapper w) {}
process2(5);                     // ❌ now a compile error — good!
process2(SafeWrapper(5));        // ✅ must be explicit about it
  • A constructor taking exactly one argument doubles as an implicit conversion unless marked explicit.
  • That silent conversion is a bug magnet — a plain int quietly becoming your class type is rarely what you want.
🎯 Interview line: "I mark single-argument constructors explicit by default, unless I deliberately want the implicit conversion — it prevents a whole category of silent, hard-to-spot bugs."

8 Constructor overloading vs default arguments — the ambiguity trap

class Sample {
public:
    Sample(int x) {}
    Sample(int x, int y = 10) {}
};

Sample s(5);   // ❌ COMPILE ERROR: ambiguous!
// Both Sample(int) and Sample(int, int=10) match Sample(5) equally well
  • Constructors can be overloaded like any function — different parameter lists, resolved at compile time.
  • But default arguments effectively create an overload too — and if two candidate signatures can both satisfy the same call, the compiler refuses to guess. Ambiguous call, not a silent pick.
⚠️ Mixing default arguments with overloading is a common source of this exact error. Fix: remove the default, or remove the redundant single-arg overload.

10 Destructors — cleanup, guaranteed

  • ~ClassName() — runs automatically when an object's lifetime ends: scope exit, delete, or program termination for globals/statics.
  • No arguments, no return type, cannot be overloaded — a class has exactly one destructor. There's no call-site to select between overloads, since destruction is implicit.
  • Local (stack) objects are destroyed in reverse order of construction — LIFO, like a stack of plates.
  • Inside one object, its data members are destroyed in reverse declaration order (mirroring construction).
class Logger {
public:
    Logger()  { cout << "Logger opened\n"; }
    ~Logger() { cout << "Logger closed\n"; }
};
void run() {
    Logger a;
    Logger b;
}   // prints: "b closed" then "a closed" — reverse order
💡 Memory hook: 🏗️ Building a house — foundation first. 💥 Demolishing — roof comes down first. You destroy in the exact reverse order you built.

11 RAII — the reason destructors matter so much

📘 RAII = Resource Acquisition Is Initialization: acquire a resource in the constructor, release it in the destructor. Tie the resource's lifetime to the object's lifetime.
class FileHandle {
    FILE* f;
public:
    FileHandle(const char* path) { f = fopen(path, "r"); }
    ~FileHandle() { if (f) fclose(f); }   // guaranteed cleanup — even if an exception is thrown
};
  • Because destructors run deterministically — including during exception-driven stack unwinding — cleanup happens without needing a finally block.
  • This is exactly how std::lock_guard, std::unique_ptr, and std::fstream all work.
🎯 Interview line: "RAII binds a resource's lifetime to an object's lifetime. Stack unwinding guarantees the destructor runs even when an exception propagates, so cleanup is exception-safe without manual `finally` logic."

12 Two things intentionally NOT covered here

  • Virtual destructors — why a polymorphic base class needs one, and what leaks if it doesn't. That needs inheritance and vtables first, so it lives in the upcoming Polymorphism note.
  • Deep vs shallow copy — the default copy constructor just copies member values, which is dangerous for classes holding raw pointers. That's the entire subject of the Copy Semantics / Rule of Three-Five-Zero note coming up.
Knowing what's deliberately deferred (and why) is itself a good interview habit — it shows you see how the topics connect rather than memorizing them in isolation.

★ 30-second revision

  • 4 constructor types: default, parameterized, copy, move
  • T b = a; → copy constructor (b is being created). b = a; (b exists) → copy assignment.
  • Initializer list runs in declaration order, never list-written order
  • const / reference members / no-default-ctor members → initializer list is mandatory
  • Define any constructor → the free default constructor disappears
  • Delegating constructors (C++11): one ctor calls another via : ClassName(...)
  • explicit blocks silent single-argument conversions
  • Default arguments can make overloaded constructors ambiguous
  • Destructor: one per class, no args, runs automatically, reverse order of construction
  • RAII: acquire in constructor, release in destructor → exception-safe cleanup for free
