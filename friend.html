Friends in C++ 🤝

Sometimes an outsider needs the keys to your private room. That trusted outsider is a friend — functions and classes that break the encapsulation wall, by invitation only.

1 The problem friends solve 🚪

  • From Note 03: private members are locked — only the class's own methods can touch them. That's encapsulation.
  • But sometimes a function outside the class, or a whole other class, genuinely needs to read those private members — e.g. a function comparing two objects, or adding two objects together.
  • Making the data public just to allow this would destroy encapsulation for everyone. Too big a hammer.
  • C++'s answer: the class can explicitly grant access to a specific trusted outsider using the friend keyword. Access by invitation only.
💡 Memory hook: Your house is private 🏠. You don't hand a key to the whole street (public). But you give ONE spare key to a trusted friend 🔑 — that's the friend keyword. You choose who; they can't let themselves in.

2 Friend function — an outsider with a key

  • A friend function is a non-member function that the class grants access to its private and protected members.
  • You declare it inside the class with the friend keyword — but it is NOT a member of the class. It's defined outside, like a normal global function (no ClassName::).
  • Because it isn't a member, it has NO this pointer — it must receive the object as a parameter to work on it.
class Employee {
    int salary;                 // private!
public:
    Employee(int s) { salary = s; }

    friend void showSalary(Employee e);  // grant access (declaration)
};

// definition — NO Employee::, NO friend keyword here, takes object as param
void showSalary(Employee e) {
    cout << "Salary = " << e.salary;   // ✅ can touch private salary
}

int main() {
    Employee affan(50000);
    showSalary(affan);              // called like a normal function, NOT affan.showSalary()
}
⚠️ Call it right: a friend function is called like a normal function — showSalary(affan), NOT affan.showSalary(). It's not a member, so there's no dot-call on the object.
🎯 Interview line: "A friend function is a non-member function granted access to a class's private/protected members. It has no this pointer and takes the object as an explicit parameter."

3 The classic use — reaching into TWO objects

  • A member function has one implicit object (this). But what if you need to peek inside two objects of the class at once — like adding two Complex numbers, or comparing two employees' salaries?
  • A friend function takes both objects as parameters and can open both their private rooms.
class Employee {
    int salary;
public:
    Employee(int s) { salary = s; }
    friend Employee addSalary(Employee, Employee);
};

Employee addSalary(Employee a, Employee b) {
    return Employee(a.salary + b.salary);  // reaches into BOTH privates
}
💡 Memory hook: A member function is a host inside one house. A friend function is a marriage counsellor 💬 who is trusted to enter both houses and see what's private in each.

4 Friend class — the whole family gets keys 👨‍👩‍👧

  • If class B is declared a friend of class A, then every member function of B can access A's private and protected members.
  • Useful when two classes are tightly coupled and one needs deep access to the other (e.g. a LinkedList and its Node).
class Engine {
    int horsepower = 300;
    friend class Car;        // Car is my friend → all Car methods get in
};

class Car {
public:
    void show(Engine e) {
        cout << e.horsepower;   // ✅ allowed: Car is a friend of Engine
    }
};
💡 Memory hook: A friend function invites one guest. A friend class invites the guest's entire family 👨‍👩‍👧 — every member function of that class walks in freely.

5 Member function of one class as friend of another

  • You don't have to befriend a whole class — you can grant access to just one specific member function of another class.
  • This is the most precise form of friendship: only that single method gets the key, not the entire class.
  • It needs careful ordering (forward declaration), because the compiler must know both classes exist.
class Engine;                 // forward declaration

class Car {
public:
    void inspect(Engine& e);     // declared now, defined later
};

class Engine {
    int horsepower = 300;
    friend void Car::inspect(Engine& e);  // ONLY this one method is a friend
};

// define after both classes are fully known
void Car::inspect(Engine& e) {
    cout << e.horsepower;       // ✅ this specific method has access
}
💡 Memory hook: Three levels of trust: one function = a single guest 🧍 · one member function of a class = one specific person from a family 👤 · friend class = the whole family 👨‍👩‍👧. Pick the smallest circle that works.

6 The rules interviewers test 📜

  • Friendship is granted, not taken. A class chooses its friends from inside; an outsider can't declare itself a friend.
  • Not mutual (not symmetric). If A says B is its friend, B can see A's privates — but A cannot see B's, unless B also befriends A.
  • Not inherited. If A befriends B, B's children do NOT inherit the friendship. Friends of my parent are not automatically my friends.
  • Not transitive. A friend of a friend is not a friend. (A befriends B, B befriends C — A and C are strangers.)
  • Can be declared in any section — putting friend under private, public, or protected makes no difference; access specifiers don't apply to friend declarations.
  • A friend function has no this; a friend class's methods use their own this as normal.
🎯 Interview trap: "Is friendship inherited or mutual?" — "Neither. Friendship is not inherited, not mutual, and not transitive. It must be explicitly granted by the class that owns the private data, each time."

7 Should you use friends? ⚖️

👍 Good reasons👎 The cost
Operator overloading (e.g. << for cout) often needs a friendIt weakens encapsulation — an outsider now depends on your private layout
Two classes that are genuinely tightly coupledOveruse signals poor design — maybe the classes should be merged or redesigned
A function needing private access to two objects at onceChanges to private members can now break friend code too
⚠️ Rule of thumb: friends are a scalpel, not a default. Use them when a clean design genuinely needs them (like operator<<), not to lazily bypass encapsulation.
🎯 Interview line: "Friend functions are commonly used for operator overloading — especially operator<< and operator>> — where the left operand is a stream, not our class, so a member function won't fit."

★ 30-second revision

  • friend function = non-member with access to privates · called like f(obj) · no this · takes object as param
  • friend class = ALL methods of that class get access
  • member friend function = only ONE named method of another class gets access (needs forward declaration)
  • Friendship is granted from inside, not mutual, not inherited, not transitive
  • Can be declared in any section (private/public/protected — doesn't matter)
  • Main real use: operator overloading & tightly-coupled class pairs
  • 🔑 hooks: friend fn = one guest · friend class = whole family · use the smallest circle that works
