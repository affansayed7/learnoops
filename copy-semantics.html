Copy Semantics & Rule of Three/Five/Zero 💧

Where the compiler's free copy behavior quietly crashes your program, and the modern fix that means you almost never have to think about this again.

1 The default copy is shallow, and shallow is dangerous

Shallow copy: copies member values as-is — including pointer addresses. Two objects end up pointing at the same heap memory. This is exactly what the compiler-generated copy constructor does if you don't write your own.
class Buffer {
    int* data;
    int size;
public:
    Buffer(int n) : size(n) { data = new int[n]; }
    ~Buffer() { delete[] data; }
    // NO copy constructor written — compiler generates a shallow one
};
int main() {
    Buffer a(10);
    Buffer b = a;    // shallow copy: b.data == a.data — SAME pointer!
}  // scope ends: ~Buffer runs for b, then for a
   // b's destructor deletes the shared memory. a's destructor deletes it AGAIN.
   // DOUBLE FREE — undefined behavior, typically a crash.
💡 Hook: Shallow copy = photocopying a house key 🔑 — two keys now exist, but there's still only one house.

2 Deep copy — the fix

class Buffer {
    int* data; int size;
public:
    Buffer(int n) : size(n) { data = new int[n]; }

    Buffer(const Buffer& other) : size(other.size) {   // DEEP copy constructor
        data = new int[size];                       // own memory
        std::copy(other.data, other.data + size, data);  // copy CONTENTS, not the pointer
    }
    Buffer& operator=(const Buffer& other) {     // DEEP copy assignment
        if (this == &other) return *this;
        delete[] data;
        size = other.size;
        data = new int[size];
        std::copy(other.data, other.data + size, data);
        return *this;
    }
    ~Buffer() { delete[] data; }
};

Now Buffer b = a; allocates separate memory and copies the values — a and b can be destroyed independently, safely.

💡 Hook: Deep copy = building a second house 🏠🏠, not just a second key.

3 The Rule of Three

Rule of Three: if a class needs a custom destructor, copy constructor, OR copy assignment operator — it almost certainly needs all three.
  • Why: needing a custom destructor is a strong signal the class manages a resource manually (raw pointer, file handle...). If you don't ALSO write the copy operations, the compiler's shallow-copy defaults will corrupt that same resource — exactly the double-free above.
  • Writing a custom destructor but leaving the copy constructor/assignment as compiler defaults is one of the most common real bugs in C++ codebases.
🎯 Interview line: "If I write a destructor, I check whether I also need a copy constructor and copy assignment operator — needing one almost always means needing all three, since they all revolve around the same manually-managed resource."

4 Move semantics — copying without copying

  • Sometimes the source object is about to be discarded anyway (a temporary, or something explicitly marked with std::move). Deep-copying it is pure waste — nobody will read the source again.
  • Move instead steals the resource: copy the pointer, then null out the source so its destructor does nothing.
class Buffer {
    int* data; int size;
public:
    Buffer(Buffer&& other) noexcept          // MOVE constructor — takes an rvalue reference
        : data(other.data), size(other.size) {
        other.data = nullptr;      // steal, then null out the source
        other.size = 0;
    }
    Buffer& operator=(Buffer&& other) noexcept {   // MOVE assignment
        if (this == &other) return *this;
        delete[] data;              // free MY OWN old resource first
        data = other.data;         // steal
        size = other.size;
        other.data = nullptr;        // leave source safely empty
        other.size = 0;
        return *this;
    }
    ~Buffer() { delete[] data; }   // delete[] nullptr is a safe no-op
};

Buffer a(100);
Buffer b = std::move(a);   // move constructor runs; a.data is now nullptr
⚠️ std::move doesn't move anything itself. It's just a cast — it converts a into an rvalue reference, telling the compiler "treat this as disposable." The actual stealing happens inside whichever move constructor/assignment gets called as a result.
⚠️ Nulling out the source is mandatory. If you skip other.data = nullptr;, both the moved-from and moved-to objects end up pointing at the same memory — the exact same double-free as shallow copy, just via a different path.
💡 Hook: Copy = photocopying a document 📄📄 (slow, now two exist). Move = handing over the original 🤝 (instant, you no longer have it).

5 The Rule of Five (C++11)

Rule of Five: the Rule of Three, plus the move constructor and move assignment operator. If a class manages a resource, these five typically travel together:
The FiveSignature
Destructor~T();
Copy constructorT(const T&);
Copy assignmentT& operator=(const T&);
Move constructorT(T&&) noexcept;
Move assignmentT& operator=(T&&) noexcept;
⚠️ Mark move operations noexcept. If they aren't, std::vector will fall back to the (slower) copy operations during reallocation — because the standard library needs a guarantee moves can't throw partway through, to preserve exception safety.

6 The Rule of Zero — the modern, preferred answer

Rule of Zero: design classes so they need none of the five, by holding resources in types that already manage themselves — std::vector, std::string, std::unique_ptr.
// ❌ Rule of Three violated — custom destructor, but no copy ctor/assignment
// → compiler's shallow-copy defaults will double-free this
class Bad {
    int* p;
public:
    Bad() { p = new int; }
    ~Bad() { delete p; }
};

// ✅ Rule of Zero — no destructor, no copy ops, no move ops written. Zero bugs.
class Good {
    std::vector<int> data;   // vector already correctly handles copy, move, AND destruction
};
  • Good needs zero hand-written special member functions — the compiler-generated ones are already correct, because vector's own copy/move/destructor do the right thing, and Good's defaults just call those.
  • This is how modern C++ is actually written: wrap raw resources in one RAII type, then compose classes out of RAII types, and stop hand-managing memory entirely.
🎯 Interview line: "My default goal is the Rule of Zero — hold resources in `unique_ptr` or standard containers so the compiler-generated special member functions are already correct. I only write the Rule of Five by hand when a class is itself the thing directly managing a raw resource."

★ 30-second revision

  • Default copy = shallow (copies pointer values) → two objects sharing memory → double free on destruction
  • Deep copy = allocate new memory, copy contents, not the address
  • Rule of Three: destructor, copy ctor, copy assignment — need one, need all three
  • Move = steal the pointer + null the source. std::move itself doesn't move — it's just a cast to rvalue reference
  • Rule of Five: add move ctor + move assignment, mark both noexcept
  • Rule of Zero (preferred): use vector/unique_ptr so you need none of the five
