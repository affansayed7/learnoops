1 What is OOP — and why does industry use it?

Definition: Object-Oriented Programming is a paradigm that models a program as a collection of interacting objects, each bundling state (data) and behaviour (methods). It gives importance to data over functions.
  • Procedural code asks “what steps?” — OOP asks “what things exist, and what can each do?”
  • Procedural pain points OOP fixes: global data with no protection, copy-paste reuse, spaghetti dependencies, poor real-world modelling.
  • Bottom-up design: build objects, compose them into a system.
🏭 Industry framing: Every backend you'll touch is objects. A payments service has Transaction, Account, Ledger. When a new payment method appears, you add a class — you don't rewrite the engine. That's the business case: change is local, not global.
🎯 Say this: “OOP organises a program around objects that combine state and behaviour. Compared to procedural code it gives us encapsulation for data safety, inheritance and polymorphism for reuse and extensibility, and a structure that maps naturally onto real-world entities — which is why it scales to large teams and codebases.”

2 Class vs Object

Class = a blueprint/template. Defining it allocates no memory.
Object = a real instance of that class. Creating it allocates memory.
💡 Hook: Class = cookie cutter 🍪✂️ · Object = the cookie. You can't eat the cutter.
🎯 Say this: “A class is a blueprint that defines structure and behaviour but occupies no memory; an object is an instance of it, and memory is allocated per object for its non-static data members.”

3 Encapsulation 🔒

Definition: Bundling data and the methods that operate on it into a single unit (the class), and restricting direct access to that data from outside — forcing access through a controlled interface.
  • It is not secrecy — it's controlled access. The setter is a checkpoint that can validate.
  • Without it you're back to Note 01's global-data chaos: anyone can write garbage into your state and you can't find who.
class Account {
    double balance;                 // 🔒 nobody touches this directly
public:
    void deposit(double amt) {
        if (amt <= 0) return;        // 🛂 the checkpoint
        balance += amt;
    }
    double getBalance() const { return balance; }  // read-only view
};
🏭 Industry framing: This is why balance is never public in a real banking system. Every mutation goes through a method that can validate, log, and audit. Public data = no audit trail = failed compliance review.
💡 Hook: 💊 Capsule — the medicine is sealed; you swallow it whole, you don't touch the powder.
🎯 Say this: “Encapsulation binds data and methods together and hides internal state behind a public interface, so invariants can be enforced in one place instead of trusting every caller.”

4 Abstraction 🎛️

Definition: Exposing only the essential interface and hiding the implementation complexity behind it.
⚠️ The #1 asked distinction: Encapsulation hides DATA (access control, the how it's stored). Abstraction hides COMPLEXITY (design, the how it works). Encapsulation is implementation-level; abstraction is design-level. They travel together but answer different questions.
💡 Hook: 🚗 Accelerator pedal — press to go. Fuel injection is not your problem.
🎯 Say this: “Abstraction is about what an object does; encapsulation is about how its data is protected. In C++, abstraction is achieved via abstract classes and interfaces, encapsulation via access specifiers.”

5 Access specifiers — the bouncer 🎟️

Accessible fromprivate 🔴protected 🟡public 🟢
Same class (its own methods)✓✓✓
Derived (child) class✗✓✓
Outside (main, via object)✗✗✓
  • Enforced at compile time — the bouncer stops you at the door, not inside.
  • Default in a class is private; default in a struct is public. That is the only difference between them in C++.
💡 Hook: 🔴 vault (staff) · 🟡 family lounge (family + children) · 🟢 dance floor (everyone).
🎯 Say this: “Access control in C++ is a compile-time mechanism. protected exists specifically to give derived classes access while still denying the outside world.”

6 Constructors 👶

Definition: A special member function that runs automatically when an object is created, used to initialise it. Same name as the class, no return type (not even void).

The four you must know

TypeSignatureWhen it runs
DefaultAccount()Account a; — no args
ParameterisedAccount(double b)Account a(500);
CopyAccount(const Account&)Account b = a; · pass/return by value
Move (C++11)Account(Account&&)Account b = std::move(a);
class Account {
    double balance;
    string owner;
public:
    Account() : balance(0), owner("unknown") {}            // default
    Account(double b, string o) : balance(b), owner(o) {}   // parameterised
    Account(const Account& other)                          // copy
        : balance(other.balance), owner(other.owner) {}
};

Member initialiser list — : balance(b)

  • Initialises members before the constructor body runs — it's initialisation, not assignment.
  • Mandatory for: const members, reference members, and base-class / member objects without a default constructor.
  • More efficient: assignment in the body would default-construct then overwrite.
⚠️ Classic trap: members are initialised in the order they are declared in the class, NOT the order in the initialiser list. Write them in declaration order or the compiler warns.
⚠️ Second trap: if you define any constructor, the compiler stops generating the implicit default one. Account a; then fails to compile.
💡 Hook: 🏨 Hotel check-in — the room is prepared the moment you arrive, automatically.
🎯 Say this: “A constructor initialises an object at creation. I prefer the member initialiser list because it initialises directly rather than default-constructing then assigning, and it's required for const and reference members.”

7 Destructors 👋

Definition: ~Account() — runs automatically when an object is destroyed (goes out of scope, or delete is called). Used to release resources. No arguments, no return type, cannot be overloaded — exactly one per class.
  • Order: objects are destroyed in reverse order of creation (stack discipline — last in, first out).
  • This is the engine of RAII: acquire in the constructor, release in the destructor — and cleanup happens even if an exception is thrown.
🏭 Industry framing: RAII is why C++ doesn't need finally. A lock_guard takes a mutex in its constructor and releases it in its destructor — so the lock is released even if the function throws. Same for file handles, DB connections, sockets.
💡 Hook: 🏨 Check-out — the room is cleaned after you leave. The tilde ~ is a waving hand 👋.
🎯 Say this: “Destructors give deterministic cleanup. That's the basis of RAII — tie a resource's lifetime to an object's lifetime, and the language guarantees release, exception-safe, in reverse construction order.”

8 The this pointer

Definition: An implicit pointer passed to every non-static member function, holding the address of the object that invoked it.
  • Resolves shadowing: this->balance = balance; when the parameter has the same name.
  • Enables method chaining: return *this by reference → obj.setA(1).setB(2).setC(3);
  • Static functions have NO this — there's no invoking object.
  • Explains the memory model: data is per-object, member functions exist once — this tells the shared function whose data to touch.
class Builder {
    int w, h;
public:
    Builder& setW(int w) { this->w = w; return *this; }  // chaining
    Builder& setH(int h) { this->h = h; return *this; }
};
Builder b;
b.setW(10).setH(20);      // ← this is why fluent APIs work
💡 Hook: this = the word “my”. this->balance reads as “my balance”.
🎯 Say this: “this is an implicit parameter to every non-static member function. It disambiguates shadowed names and, returned as *this, enables fluent interfaces.”

9 Static members 📋

Static data member: one copy shared by the whole class, not one per object. Exists before any object is created.
Static member function: belongs to the class, callable as Class::fn() with no object, has no this, and can therefore access only static members.
class Account {
    int id;
public:
    static int count;                  // declaration only
    Account() { count++; id = count; }
    static void total() {              // no `this`
        cout << count;                  // ✅ static
        // cout << id;                  // ❌ which object's id?!
    }
};
int Account::count = 0;                // definition — REQUIRED, once, outside
⚠️ The trap: forget int Account::count = 0; and you get a linker error, not a compile error. The in-class line only declares; it allocates no storage.
🏭 Industry framing: Static members back counters, caches, config, and the Singleton pattern — anything that's genuinely one-per-process rather than one-per-object.
💡 Hook: Your own desk 🗄️ = normal data · the shared whiteboard 📋 on the wall = static data.
🎯 Say this: “A static member belongs to the class, not to any instance. A static member function has no this pointer, which is exactly why it can only touch static members — and why it can't be const.”

10 Friends 🤝

Friend function: a non-member function granted access to a class's private/protected members. No this; takes the object as a parameter; called as f(obj), not obj.f().
Friend class: all member functions of that class get access.
Member friend function: only one named method of another class gets access.
  • Granted, not taken — the class chooses, from inside.
  • Not mutual · not inherited · not transitive.
  • Can be declared in any section — access specifiers don't apply to friend declarations.
🏭 Industry framing: The honest reason friends exist: operator<<. The left operand is ostream, not your class, so it can't be a member function — but it needs your privates to print them. That's the canonical legitimate use.
class Account {
    double balance;
public:
    friend ostream& operator<<(ostream& os, const Account& a);
};
ostream& operator<<(ostream& os, const Account& a) {
    return os << "₹" << a.balance;   // reaches private balance
}
cout << myAccount;                    // clean call site
⚠️ Use sparingly: a friend is a scalpel, not a default. Every friend is code outside the class that now depends on its private layout.
💡 Hook: friend fn = one guest with a spare key 🔑 · friend class = the whole family 👨‍👩‍👧. Pick the smallest circle that works.
🎯 Say this: “Friendship is an explicit, one-directional grant of access. It's not inherited, not mutual, not transitive. I'd reach for it mainly for operator overloading like operator<<, where a member function isn't an option.”

🔥 Most-asked questions (Part 1 scope)

Click to reveal. Try answering out loud first — speaking is the skill being tested, not recognition.

What is the difference between a class and an object?
A class is a blueprint defining structure and behaviour; it occupies no memory. An object is an instance of that class; memory is allocated per object for its non-static data members. One class, many objects, each with independent state.
One-liner: Class = cookie cutter, object = the cookie.
Encapsulation vs Abstraction — the #1 asked distinction
Encapsulation hides data — it's access control, an implementation-level concern, achieved with access specifiers. Abstraction hides complexity — it's design-level, exposing only the essential interface, achieved with abstract classes/interfaces. Encapsulation asks how is the data protected; abstraction asks what does this thing do. They usually appear together, which is why people conflate them.
Say: “A car's pedal is abstraction — I press to go. The engine being sealed under the hood so I can't yank a wire is encapsulation.”
What's the only difference between class and struct in C++?
Default access. In a class, members and base classes default to private; in a struct, they default to public. Everything else — constructors, destructors, inheritance, virtual functions, access specifiers — works identically. (Convention, not language rule: struct for passive data aggregates, class for types with invariants.)
Why keep data private and expose getters/setters? Isn't that just extra typing?
Because a setter is a checkpoint. It can validate (reject a negative deposit), log, fire an event, or later change the internal representation without breaking a single caller. Public data gives up all of that permanently — once callers touch the field directly, you can never change how it's stored.
Say: “It's not about secrecy, it's about being able to enforce invariants in one place.”
Is an access violation on a private member a compile-time or runtime error?
Compile-time. C++ access control is enforced entirely by the compiler; the program never builds, so nothing runs. It's a language-level check, not a security mechanism — with casts and pointer tricks the bytes are still reachable at runtime.
What is a constructor? Can it be virtual?
A constructor initialises an object at creation: same name as the class, no return type, runs automatically. It cannot be virtual — virtual dispatch needs a vtable pointer, and that pointer is set up by the constructor. The object's dynamic type doesn't exist yet, so there's nothing to dispatch on.
Say: “You can't dispatch on a type that isn't constructed yet — the vptr is initialised during construction.”
Why use a member initialiser list instead of assigning in the constructor body?
Three reasons: (1) It initialises rather than default-constructs-then-assigns — cheaper for non-trivial members. (2) It's mandatory for const members, reference members, and base/member objects lacking a default constructor. (3) It expresses intent. Trap to mention: members initialise in declaration order, not list order.
If I write a parameterised constructor, can I still do `Account a;`?
No. Defining any constructor suppresses the compiler-generated default constructor, so Account a; fails to compile. You must write your own default constructor, or Account() = default; in C++11.
Can a destructor be overloaded? Can it take arguments?
No to both. A class has exactly one destructor — no arguments, no return type, no overloading. Reason: destruction is invoked implicitly by the compiler when scope ends or delete is called, so there's no call site to pass arguments at, and no signature to select between.
In what order are objects destroyed?
Reverse order of construction — LIFO, like a stack of plates. Within an object: the destructor body runs first, then members are destroyed in reverse declaration order, then base classes. This is what makes RAII composable and exception-safe.
What is RAII and why does C++ not need `finally`?
Resource Acquisition Is Initialisation: bind a resource's lifetime to an object's lifetime. Acquire in the constructor, release in the destructor. Because destructors run deterministically — including during stack unwinding when an exception propagates — cleanup is guaranteed without a finally block. std::lock_guard, std::unique_ptr, and std::fstream are all RAII types.
Industry: “A lock_guard releases the mutex even if the function throws — that's RAII paying rent.”
What is the `this` pointer? Do static functions have one?
this is an implicit pointer to the invoking object, passed to every non-static member function. It disambiguates shadowed parameter names and enables method chaining via return *this. Static functions have no this — they belong to the class, not an instance.
Why can't a static member function be `const`?
Because const on a member function is a promise about this — that the function won't modify the object it was called on. A static function has no this, so the qualifier has nothing to qualify. The compiler rejects it.
This is a favourite because it tests whether you understand why rather than memorised a rule.
Why must a static data member be defined outside the class?
The in-class line is only a declaration — it allocates no storage. Since the header may be included in many translation units, defining it in-class would create multiple definitions. The out-of-class definition (int Account::count = 0;) gives it storage exactly once. Forget it and you get a linker error, not a compiler error. (C++17's inline static lets you skip this.)
Can a static member function access non-static data members?
No. Without a this pointer it has no idea which object's data you'd mean. It can access only static data members and other static functions — unless you explicitly hand it an object as a parameter, in which case it can use that object's members through it.
What is a friend function? Doesn't it break encapsulation?
A non-member function explicitly granted access to a class's private members. It has no this and takes the object as a parameter. It's controlled weakening, not a break: the class chooses its friends from inside, so the interface is still deliberate. Overuse is a design smell; the canonical legitimate use is operator<<, where the left operand is a stream so a member function isn't possible.
Is friendship inherited, mutual, or transitive?
None of the three. If A grants friendship to B: B is not automatically A's friend in reverse (not mutual); B's derived classes don't inherit the access (not inherited); and a friend of B gains nothing on A (not transitive). Each grant is explicit and one-directional.
One-liner: “My friend's children aren't my friends, and neither are my friend's friends.”
Does it matter which section a friend declaration goes in?
No. Access specifiers don't apply to friend declarations — friend void f(X); grants identical access whether it sits under private:, protected:, or public:. It feels like it should matter, which is exactly why it's asked.
How is an object laid out in memory? Does each object store its own copy of the methods?
No. Each object stores its own non-static data members (plus padding, plus a vptr if the class has virtual functions). Member functions exist once in a shared code section — the this pointer tells the shared function which object's data to operate on. Static data members are stored once for the whole class, outside any object.
Why is OOP better than procedural for a large system? (the "so what" question)
Because change stays local. In procedural code, global data plus tangled function dependencies mean one edit ripples unpredictably — the bug's symptom and cause live in different files. OOP gives ownership boundaries: state is private behind an interface, so invariants are enforced in one place; inheritance and polymorphism let you add a new type without touching the code that consumes it. That's what makes it survive large teams.
Say: “Add a payment method by adding a class — not by editing a 400-line switch statement.”
