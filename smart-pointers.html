Smart Pointers 🧠

The Rule of Zero in practice — RAII wrappers that make manual new/delete almost entirely unnecessary in modern C++.

1 The problem they solve

Shape* s = new Circle();
doSomethingRisky();   // if this throws, `delete s;` below never runs → LEAK
delete s;
Smart pointer: an RAII wrapper around a raw pointer that owns the memory and frees it automatically in its own destructor — exception-safe by construction, exactly like the Rule of Zero from Note 11.

2 unique_ptr — exclusive ownership, the default choice

auto e = std::make_unique<Employee>("Alex");
e->raiseSalary();
// automatically deleted when e goes out of scope — no manual delete, ever
  • Exactly one owner at a time. Copying is disabled — the copy constructor and copy assignment are = deleted.
  • Ownership can only be transferred via move.
  • Zero runtime overhead compared to a raw pointer — no reference counting.
std::unique_ptr<Employee> e1 = std::make_unique<Employee>("Alex");
std::unique_ptr<Employee> e2 = e1;              // ❌ compile error — copy constructor is deleted
std::unique_ptr<Employee> e3 = std::move(e1);   // ✅ ownership transferred — e1 is now nullptr
💡 Hook: unique_ptr = the only key to a flat 🔑 — you can hand it to someone else, but you can't photocopy it.

3 shared_ptr — reference-counted shared ownership

std::shared_ptr<Employee> a = std::make_shared<Employee>("Alex");
std::shared_ptr<Employee> b = a;    // ✅ allowed — refcount becomes 2
cout << a.use_count();               // 2
b.reset();                           // refcount drops to 1
// object is destroyed only when the LAST shared_ptr pointing to it is gone (refcount hits 0)
⚠️ Classic mistake — constructing two independent shared_ptrs from the same raw pointer:
Employee* raw = new Employee("Alex");
std::shared_ptr<Employee> a(raw);
std::shared_ptr<Employee> b(raw);   // ❌ WRONG — creates a SECOND, independent control block
// a and b each think their own refcount is 1, unaware of each other
// both will eventually try to delete raw → DOUBLE FREE
// correct way: std::shared_ptr b = a;  (copy the shared_ptr, not the raw pointer)
💡 Hook: shared_ptr = flatmates 👥 — the last one to move out turns off the lights (frees the memory).

4 weak_ptr — breaking reference cycles

Two shared_ptrs pointing at each other never reach a refcount of zero — the classic memory leak reference counting can't solve on its own:

class Node {
public:
    std::shared_ptr<Node> next;    // owns the next node
    std::weak_ptr<Node> prev;      // OBSERVES the previous node — doesn't bump its refcount
};
  • weak_ptr holds a non-owning reference — it doesn't increment the refcount, so it can't keep an object alive by itself.
  • To actually use it, call .lock(), which returns a shared_ptr if the object still exists, or an empty one if it's already been destroyed.
💡 Hook: weak_ptr = a visitor 👀 who can look in, but doesn't pay rent — so they never stop the lease from ending.

5 Two more traps

std::unique_ptr<int> p = std::make_unique<int>(5);
int* raw = p.get();     // exposes the raw pointer — does NOT transfer ownership
delete raw;              // ❌ DANGER — p still thinks it owns this memory
// when p's own destructor runs later, it deletes the SAME memory again → double free
⚠️ .get() is for passing the raw pointer to an API that needs one (e.g. a C library) — never for manually managing its lifetime yourself. The smart pointer still believes it owns that memory.
🎯 Interview line: "I default to unique_ptr — it's zero-overhead and expresses exclusive ownership clearly. I only reach for shared_ptr when ownership is genuinely shared, since the atomic refcount isn't free, and I use weak_ptr specifically to break cycles that reference counting can't collect on its own."

6 Custom deleters & why make_unique/make_shared

// wrapping a C API that needs its own cleanup function
std::unique_ptr<FILE, decltype(&fclose)> file(fopen("data.txt", "r"), &fclose);
// file automatically calls fclose() on the FILE* when it goes out of scope
  • Always prefer make_unique/make_shared over raw new: they're exception-safe (no window where a raw pointer exists briefly unowned), and make_shared specifically allocates the object and its control block in one allocation instead of two.

★ 30-second revision

  • unique_ptr: exclusive owner, move-only, zero overhead. Default choice.
  • shared_ptr: reference-counted shared ownership. Never construct two directly from the same raw pointer — always copy an existing shared_ptr.
  • weak_ptr: non-owning observer, breaks reference cycles, use .lock() to access
  • .get() exposes the raw pointer without transferring ownership — never manually delete it
  • Prefer make_unique/make_shared over raw new — exception safety + (for shared) one allocation instead of two
