Inheritance 🧬

The mechanism, the five shapes it comes in, the order things get built and torn down, and the diamond that breaks all of it.

1 What inheritance actually is

Definition: A mechanism where a derived class acquires the members of a base class, modeling an "is-a" relationship (a Dog is an Animal).
  • The derived class gets everything the base has, plus whatever new members it adds.
  • Every member is inherited — including private ones. The catch: private members are still physically part of the derived object, but the derived class's own code cannot touch them directly. They're only reachable through the base's own public/protected methods.
class Animal {
    int age;              // private — exists in every Dog object too, but Dog can't touch it directly
public:
    void setAge(int a) { age = a; }
    int getAge() const { return age; }
};
class Dog : public Animal {
public:
    void bark() { // cout << age;   // ❌ error: age is private in Animal }
};
💡 Common misconception, corrected: "private members aren't inherited" is wrong. They ARE inherited (they exist in memory) — they're just inaccessible to the derived class's own code.

3 Access modes — public / protected / private inheritance

C++ is unusual: how you inherit changes what the outside world can see through the derived class.

Base member ↓ / Mode →public inheritanceprotected inheritanceprivate inheritance
publicstays publicbecomes protectedbecomes private
protectedstays protectedstays protectedbecomes private
private✗ never accessible✗ never accessible✗ never accessible
  • The inheritance mode is a ceiling, not a floor — it can only make access more restricted, never less.
  • Default mode: class D : B is private inheritance. struct D : B is public inheritance. (Yet another class/struct default — same family as member-access defaults.)
  • Only public inheritance models a true is-a relationship. Private inheritance means "implemented in terms of" — usually better expressed as composition instead.
💡 Memory hook: Private base members are a locked room in the house you inherited — you own the house, but you never get that key, no matter how you inherited it.
🎯 Interview line: "Only public inheritance genuinely models is-a. Private and protected inheritance restrict what the outside world can see through the derived class — they're implementation techniques, not subtyping."

4 Construction & destruction order

Rule: Construction goes base → derived. Destruction goes derived → base — always the exact reverse.
class Animal {
    string name;
public:
    Animal(string n) : name(n) { cout << "Animal ctor: " << name << "\n"; }
    ~Animal() { cout << "Animal dtor: " << name << "\n"; }
};
class Dog : public Animal {
    string breed;
public:
    Dog(string n, string b) : Animal(n), breed(b) { cout << "Dog ctor\n"; }
    ~Dog() { cout << "Dog dtor\n"; }
};
int main() { Dog d("Rex", "Labrador"); }

// Output:
// Animal ctor: Rex   ← base finishes completely first
// Dog ctor
// Dog dtor           ← derived torn down first
// Animal dtor: Rex
  • Dog(n) passes n to Animal's constructor via the member initializer list — : Animal(n), breed(b).
  • If you don't mention the base in the initializer list, the compiler tries to call the base's default constructor automatically. If Animal has no default constructor (because it only has the parameterized one above), that's a compile error.
⚠️ Why virtual calls in constructors don't dispatch to derived overrides: the base constructor runs to completion before the derived part exists — during that window, the object genuinely is just a Base. (Full mechanics live in the Polymorphism note.)
💡 Hook: 🏗️ Foundation before walls (construction). 💥 Roof comes down before the foundation (destruction). You can't build on a floor that doesn't exist yet.

5 A trap that lives here, not in polymorphism: name hiding

class Base {
public:
    void show(int x) { cout << "Base::show(int)\n"; }
};
class Derived : public Base {
public:
    void show(double x) { cout << "Derived::show(double)\n"; }
};
int main() {
    Derived d;
    d.show(5);   // prints "Derived::show(double)" — NOT Base::show(int)!
}
  • C++ name lookup is scope-based: once the compiler finds any show in Derived's scope, it stops looking in Base entirely — even though Base::show(int) would be an exact-type match.
  • This has nothing to do with virtual — it's pure name hiding from inheritance's scoping rules.
  • Fix: add using Base::show; inside Derived to pull the base overloads back into scope alongside the new one.
⚠️ This is one of the most surprising things about C++ inheritance for people coming from languages with different overload rules. Declaring any same-named member in a derived class hides the entire base overload set for that name.

6 The diamond problem 💎

Problem: In hybrid/multiple inheritance, if B and C both inherit from A, and D inherits from both B and C — D ends up with two separate copies of A. Any access to A's members through D becomes ambiguous.
class Person { public: string name; };
class Student  : public Person {};
class Employee : public Person {};
class TA : public Student, public Employee {};

TA t;
t.name = "Alex";   // ❌ error: request for member 'name' is ambiguous
// t has TWO Person subobjects — one via Student, one via Employee
// workaround without fixing the design: t.Student::name = "Alex";  ← ugly
class Person { public: string name; };
class Student  : virtual public Person {};   // virtual → share the Person
class Employee : virtual public Person {};
class TA : public Student, public Employee {};

TA t;
t.name = "Alex";   // ✅ unambiguous — only one Person exists
💡 Hook: 💎 Without virtual, TA inherits two grandparents who happen to be the same person — "whose surname do I use?" is genuinely unanswerable. virtual says: there's only one grandparent.
🎯 Interview line: "The diamond problem is a duplicated base subobject from multiple inheritance. C++ fixes it with virtual inheritance, making derived classes share one base subobject. Java sidesteps the whole issue by disallowing multiple class inheritance — only multiple interfaces, which carry no state to duplicate."

7 Bonus trap: who constructs the shared virtual base?

This one genuinely surprises people, and it's an excellent differentiator in an interview:

class Person {
public:
    string name;
    Person(string n) : name(n) { cout << "Person ctor\n"; }
};
class Student : virtual public Person {
public:
    Student(string n) : Person(n) { cout << "Student ctor\n"; }
};
class Employee : virtual public Person {
public:
    Employee(string n) : Person(n) { cout << "Employee ctor\n"; }
};
class TA : public Student, public Employee {
public:
    // The MOST-DERIVED class must initialize the virtual base directly —
    // Student's and Employee's own "Person(n)" calls are IGNORED here!
    TA(string n) : Person(n), Student(n), Employee(n) { cout << "TA ctor\n"; }
};
  • Because there's only one Person subobject, only one piece of code can be responsible for constructing it — and the C++ standard makes that the most-derived class, always.
  • Student's and Employee's own Person(n) calls in their initializer lists are silently ignored when they're not the most-derived class being built. TA must mention Person explicitly in its own initializer list, even though Person isn't its direct base.
  • Forget it, and Person gets built with whatever its default constructor would do — a compile error here, since Person has none.
⚠️ Most people writing virtual inheritance for the first time get bitten by this exact thing. It's a genuinely strong "I know this cold" signal if you bring it up unprompted.

8 Composition vs inheritance — the design judgment call

  • is-a → inheritance. A SportsCar is a Car.
  • has-a → composition. A Car has an Engine — don't make Car inherit from Engine.
// ❌ wrong relationship — a Car is not a kind of Engine
class Car : public Engine { };

// ✅ composition — a Car HAS an Engine
class Car {
    Engine engine;    // member, not base class
public:
    void start() { engine.ignite(); }
};
⚠️ Modern guidance: "prefer composition over inheritance." Inheritance couples the derived class tightly to the base's implementation — a base change ripples everywhere, and you can't swap behavior at runtime. Composition keeps things swappable and testable.
💡 Hook: Inheritance is a birth certificate — permanent, fixed at creation. Composition is a toolbox — you can swap tools in and out.
🎯 Interview line: "I default to composition for reuse and reserve inheritance for genuine is-a subtyping — inheritance couples you to the base's implementation in a way that's hard to undo later."

★ 30-second revision

  • 5 types: single, multilevel, multiple, hierarchical, hybrid
  • Private base members ARE inherited (they exist), just not directly accessible
  • Access mode is a ceiling: public → stays same, protected → caps at protected, private → caps at private. Base private members: never accessible regardless.
  • Default: class D : B → private inheritance. struct D : B → public inheritance.
  • Construction: base → derived. Destruction: derived → base. Reverse, always.
  • Name hiding: any same-named member in Derived hides ALL of Base's overloads for that name — fix with using Base::name;
  • Diamond problem: duplicated base via multiple inheritance → ambiguous access. Fixed with virtual inheritance.
  • Virtual base construction: the most-derived class is always responsible for it directly, even through intermediate classes
  • Prefer composition (has-a) over inheritance (is-a) for reuse
