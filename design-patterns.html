OOP Interview Prep · Note 15

Design Principles & Patterns 🏛️🧩

SOLID plus the four design patterns that actually get asked — with real ❌→✅ code, not just definitions.

1 SOLID — five principles, five real fixes

S

Single Responsibility — one reason to change

A class should do exactly one job.

// ❌ Invoice does THREE unrelated jobs
class Invoice {
public:
    double calculateTotal() { return 100; }
    void printToPDF() { /* rendering logic */ }
    void emailToCustomer() { /* mail logic */ }
};
// ✅ split by responsibility
class Invoice { public: double calculateTotal() { return 100; } };
class InvoiceRenderer { public: void printToPDF(const Invoice&) {} };
class InvoiceMailer { public: void emailToCustomer(const Invoice&) {} };
O

Open/Closed — open to extension, closed to modification

Add features by adding code, not editing working code.

// ❌ must edit this function every time a new payment type appears
double processPayment(string type, double amt) {
    if (type == "credit") { /*...*/ }
    else if (type == "upi")    { /*...*/ }  // keep adding branches forever
    return amt;
}
// ✅ new payment method = new class, ZERO changes to existing code
class PaymentMethod { public: virtual void pay(double) = 0; virtual ~PaymentMethod()=default; };
class CreditCard : public PaymentMethod { public: void pay(double) override {} };
class UPI : public PaymentMethod { public: void pay(double) override {} };
L

Liskov Substitution — a subtype must be truly substitutable

Code written against the base must keep working, unmodified, for any derived type.

class Rectangle {
protected:
    int width, height;
public:
    virtual void setWidth(int w)  { width = w; }
    virtual void setHeight(int h) { height = h; }
    int area() const { return width * height; }
};
class Square : public Rectangle {   // "a square IS a rectangle" — feels right, but...
public:
    void setWidth(int w)  override { width = height = w; }   // forces both dimensions
    void setHeight(int h) override { width = height = h; }
};
void test(Rectangle& r) {
    r.setWidth(5); r.setHeight(4);
    assert(r.area() == 20);   // PASSES for Rectangle, FAILS for Square (area is 16!)
}
⚠️ The lesson: is-a is about behavior, not vocabulary. "A square is mathematically a rectangle" is true in geometry — but Square can't honor Rectangle's contract (independently settable width/height) without breaking it. That makes the inheritance wrong, regardless of how natural the English sentence sounds.
I

Interface Segregation — many small interfaces beat one fat one

Don't force a class to implement methods it doesn't need.

// ❌ fat interface forces meaningless implementations
class IMachine { public: virtual void print()=0; virtual void scan()=0; virtual void fax()=0; };
class SimplePrinter : public IMachine {
public:
    void print() override { /*...*/ }
    void scan() override { throw std::logic_error("unsupported"); }  // forced to stub this out
    void fax()  override { throw std::logic_error("unsupported"); }
};
// ✅ segregated — SimplePrinter only implements what it actually does
class IPrinter { public: virtual void print()=0; virtual ~IPrinter()=default; };
class SimplePrinter : public IPrinter { public: void print() override {} };
D

Dependency Inversion — depend on abstractions, not concretions

High-level logic shouldn't hard-code low-level details.

// ❌ OrderService is glued to ONE concrete database — can't swap, can't test
class MySQLDatabase { public: void save(string d) {} };
class OrderService {
    MySQLDatabase db;
public: void placeOrder() { db.save("order"); }
};
// ✅ depend on the ABSTRACTION — now a mock can be injected in tests
class IDatabase { public: virtual void save(string)=0; virtual ~IDatabase()=default; };
class MySQLDatabase : public IDatabase { public: void save(string d) override {} };
class OrderService {
    IDatabase& db;
public: OrderService(IDatabase& d) : db(d) {}
    void placeOrder() { db.save("order"); }
};
🏭 The honest reason SOLID matters: testability. Dependency Inversion is specifically what lets you inject a MockDatabase in unit tests instead of hitting a real database. Mentioning testing unprompted signals you've actually shipped software.
💡 If you blank on a letter: L is Liskov — remember the square/rectangle story and you'll reconstruct the rest.

2 The four patterns that actually get asked

① Singleton — exactly one instance

class Logger {
    Logger() = default;
public:
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;
    static Logger& get() {
        static Logger instance;      // thread-safe initialization guaranteed since C++11
        return instance;
    }
    void log(const string& m) { cout << m; }
};
Logger::get().log("started");
⚠️ This is the Meyers Singleton. Since C++11, initialization of a function-local static is guaranteed thread-safe and lazy — no manual locking needed. Worth mentioning the criticism too: singletons are global state, which hurts testability. Many teams prefer passing dependencies explicitly instead.

② Factory — create without naming the concrete class

class Shape { public: virtual void draw() = 0; virtual ~Shape() = default; };
class Circle : public Shape { public: void draw() override { cout << "Circle"; } };
class Square : public Shape { public: void draw() override { cout << "Square"; } };

class ShapeFactory {
public:
    static std::unique_ptr<Shape> create(const string& type) {
        if (type == "circle") return std::make_unique<Circle>();
        if (type == "square") return std::make_unique<Square>();
        return nullptr;
    }
};
auto s = ShapeFactory::create("circle");
s->draw();

Object creation lives in one place. The caller never names Circle or Square directly — only the factory knows the concrete types.

③ Strategy — swap an algorithm at runtime

class SortStrategy { public: virtual void sort(std::vector<int>&) = 0; virtual ~SortStrategy()=default; };
class QuickSort  : public SortStrategy { public: void sort(std::vector<int>& v) override { /*...*/ } };
class BubbleSort : public SortStrategy { public: void sort(std::vector<int>& v) override { /*...*/ } };

class Sorter {
    std::unique_ptr<SortStrategy> strategy;    // COMPOSITION — a swappable member, not a fixed base class
public:
    void setStrategy(std::unique_ptr<SortStrategy> s) { strategy = std::move(s); }
    void run(std::vector<int>& v) { strategy->sort(v); }
};
Sorter sorter;
sorter.setStrategy(std::make_unique<QuickSort>());
sorter.run(data);   // swap the algorithm any time, without changing Sorter at all
💡 Strategy is "prefer composition over inheritance" made concrete — behavior is a member you can replace, not a base class you're locked into.

④ Observer — publish/subscribe

class Observer { public: virtual void update(int v) = 0; virtual ~Observer()=default; };
class Display : public Observer {
public: void update(int v) override { cout << "Display shows: " << v; }
};
class Subject {
    std::vector<Observer*> observers;
public:
    void attach(Observer* o) { observers.push_back(o); }
    void setValue(int v) {
        for (auto* o : observers) o->update(v);   // notify EVERY subscriber
    }
};
Display d; Subject s;
s.attach(&d);
s.setValue(42);   // "Display shows: 42"

One-to-many: when the subject changes, every subscriber hears about it automatically. This is every UI event system and message bus you've used.

🎯 Interview line: "Patterns are named solutions to recurring design problems — a shared vocabulary. I reach for Strategy and Factory routinely; I'm more cautious with Singleton because it's global state that makes testing harder."

3 The honest caveat: patterns aren't the goal

  • A pattern is a named solution to a recurring problem — not something to apply for its own sake.
  • Wrapping a single, never-changing algorithm in a full Strategy hierarchy, or building a Factory for a class with exactly one implementation, is overengineering — added indirection with no real payoff.
  • The best interview answer often isn't "I'd use pattern X" — it's explaining what problem you're solving, and reaching for a pattern because it fits, not to sound sophisticated.
🎯 Say this if asked to "design X": "I'd start with the simplest thing that works, and reach for a pattern like Strategy or Factory specifically when I see the problem it's meant to solve — like needing to swap behavior at runtime, or centralizing object creation."

★ 30-second revision

  • Single Responsibility · Open/Closed · Liskov Substitution · Interface Segregation · Dependency Inversion
  • LSP's classic violation: Square overriding Rectangle's setters breaks code written against Rectangle
  • DIP's real payoff: testability — depend on interfaces so mocks can be injected
  • Singleton: Meyers pattern, thread-safe since C++11, but global state hurts testing
  • Factory: centralizes object creation, caller never names the concrete class
  • Strategy: composition-based, swappable algorithm at runtime
  • Observer: one-to-many notification — the basis of most event systems
  • Patterns solve real problems — don't apply one just to look sophisticated
