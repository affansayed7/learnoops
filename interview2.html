1 Inheritance 🧬

Definition: A mechanism where a derived class acquires the properties and behaviour of a base class, enabling reuse and expressing an “is-a” relationship.

The 5 types

⚠️ “is-a” vs “has-a”: Inherit only for a true is-a relationship (a SavingsAccount is an Account). If it's has-a, use composition (a Car has an Engine — don't inherit Engine!).
🏭 Industry framing: Modern guidance is “prefer composition over inheritance”. Deep hierarchies are rigid — a change in the base ripples everywhere, and you can't swap behaviour at runtime. Inheritance for interfaces, composition for reuse. Saying this unprompted signals real experience.
🎯 Say this: “Inheritance models an is-a relationship and enables polymorphism. But I default to composition for code reuse — inheritance couples the derived class to the base's implementation, so I reserve it for genuine subtyping.”

2 Access modes — public / protected / private inheritance

C++ is unusual here: how you inherit changes what the outside world sees.

Base member ↓ / Mode →publicprotectedprivate
publicpublicprotectedprivate
protectedprotectedprotectedprivate
private✗ not accessible✗ not accessible✗ not accessible
  • Private members are NEVER inherited-accessible — they exist in the object, but the derived class can't touch them directly. Use protected if children need access.
  • Default mode: class D : B is private inheritance. struct D : B is public. (Another class/struct difference!)
  • public = is-a (the only one that models subtyping) · private = implemented-in-terms-of (composition in disguise).
💡 Hook: The mode is a ceiling, not a floor 🔽 — it can only make things more restricted, never more open.
🎯 Say this: “Only public inheritance models is-a. Private inheritance means implemented-in-terms-of — and it's usually better expressed as composition.”

3 Construction & destruction order 🔄

Rule: Construction goes base → derived. Destruction goes derived → base. Always the exact reverse.
class Base {
public:
    Base()  { cout << "Base ctor\n"; }
    ~Base() { cout << "Base dtor\n"; }
};
class Derived : public Base {
public:
    Derived()  { cout << "Derived ctor\n"; }
    ~Derived() { cout << "Derived dtor\n"; }
};
int main() { Derived d; }

// Output:
// Base ctor      ← foundation first
// Derived ctor
// Derived dtor   ← reverse
// Base dtor
💡 Hook: 🏗️ Building a house — foundation before walls. Demolishing — roof before foundation. You can't stand on a floor that isn't built yet.
⚠️ Why it matters: the base is fully constructed before the derived constructor body runs — which is exactly why calling a virtual function in a constructor doesn't dispatch to the derived override. During the base constructor, the object is still a Base.
🎯 Say this: “Base constructs first so the derived class can rely on a fully-initialised base. Destruction reverses it. And that ordering is precisely why virtual dispatch in a constructor resolves to the base version.”

4 The diamond problem 💎

Problem: In hybrid/multiple inheritance, if B and C both inherit from A, and D inherits from both B and C — D ends up with two copies of A. Calls become ambiguous.
class A { public: int x; };
class B : virtual public A {};   // virtual → share the A
class C : virtual public A {};
class D : public B, public C {};

D d;
d.x = 5;   // ✅ unambiguous — only one A exists

// Without `virtual`: error: request for member 'x' is ambiguous
// Workaround without virtual: d.B::x = 5;  ← ugly, two separate x's
💡 Hook: 💎 Without virtual, D inherits two grandparents that are the same person — “whose eyes do I have?” is genuinely unanswerable. virtual says: there's only one grandpa.
🎯 Say this: “The diamond problem is ambiguity from a duplicated base in multiple inheritance. C++ solves it with virtual inheritance, which makes derived classes share a single base subobject. Java sidesteps it entirely by banning multiple class inheritance and allowing only multiple interfaces.”

5 Polymorphism 🎭 — compile-time vs runtime

Definition: “Many forms” — the same interface producing different behaviour depending on the actual type or arguments.

MechanismName mangling / signature matchvtable + vptr lookup

💡 Hook: Compile-time = choosing your meal from a fixed menu before you arrive 📋. Runtime = the chef's surprise 🍽️ — you find out what it is when it lands.
🏭 Industry framing: Runtime polymorphism is how plugins work. Your renderer holds vector<Shape*> and calls draw(). Ship a new Hexagon class next year — the renderer doesn't change one line. That's the Open/Closed Principle in the flesh.

6 Overloading vs Overriding vs Hiding ⚠️

The three get confused constantly. Nail the distinction and you look sharp.

OverloadingOverridingHiding (shadowing)
WhereSame classBase & derivedBase & derived
SignatureDifferent paramsIdentical signatureDifferent params, same name
virtual needed?NoYes (in base)No
BindingCompile-timeRuntimeCompile-time
class Base {
public:
    virtual void speak() { cout << "Base\n"; }
    void greet(int) {}
    void greet(string) {}          // OVERLOADING (same class, diff params)
};
class Derived : public Base {
public:
    void speak() override { cout << "Derived\n"; }  // OVERRIDING
    void greet(double) {}    // ⚠️ HIDES both Base::greet overloads!
};

Derived d;
d.greet(5);          // ❌ error! Base::greet(int) is HIDDEN, not overloaded
d.Base::greet(5);    // ✅ works — or add `using Base::greet;` in Derived
⚠️ Name hiding is the trap: declaring any greet in Derived hides every greet from Base — overload resolution never crosses class scope. Fix with using Base::greet;.
🎯 Say this: “Overloading is compile-time, same scope, different signatures. Overriding is runtime, requires virtual and an identical signature. Name hiding is the accidental one — any same-named member in the derived class hides the whole base overload set.”
💡 Always write override (C++11). If your signature doesn't actually match a virtual base function, the compiler errors instead of silently creating a new function. Free bug prevention — mention this and you sound senior.

7 Virtual functions & the vtable ⚙️

Virtual function: a member function declared virtual in the base, allowing a derived class to override it, so the call is resolved by the object's actual (dynamic) type at runtime — not the pointer's type.

How it actually works under the hood

  • Any class with ≥1 virtual function gets a vtable: a static, per-class array of function pointers.
  • Every object of that class gets a hidden vptr pointing to its class's vtable. (This is why sizeof grows by a pointer!)
  • A call p->draw() compiles to: follow vptr → index into vtable → call that address. One extra indirection.
  • The vptr is set by the constructor — hence virtual calls in constructors resolve to the base version.
⚠️ Rapid-fire facts: Constructors cannot be virtual (no vptr yet). Destructors should be virtual in polymorphic bases. Static functions cannot be virtual (no object). Friends cannot be virtual (not members). virtual is inherited — once virtual, always virtual, even if you omit the keyword in the derived class.
💡 Hook: vtable = a restaurant's menu 📋 (one per restaurant/class). vptr = the menu in your hand 🤲 (one per customer/object). You say “item #3”; what arrives depends on which menu you're holding.
🎯 Say this: “Virtual functions give late binding via a vtable per class and a vptr per object. The call costs one indirection and generally can't be inlined — so it's pay-for-what-you-use, not free, which is exactly C++'s philosophy.”

8 Virtual destructors ☠️ — the memory-leak question

Rule: If a class has any virtual function (i.e. it's meant to be a polymorphic base), its destructor must be virtual. Otherwise delete base_ptr is undefined behaviour — in practice, the derived destructor never runs and its resources leak.
class Base {
public:
    ~Base() { cout << "~Base\n"; }          // ❌ NOT virtual
};
class Derived : public Base {
    int* data;
public:
    Derived()  { data = new int[1000]; }
    ~Derived() { delete[] data; cout << "~Derived\n"; }
};

Base* p = new Derived();
delete p;      // prints only "~Base" → 4000 bytes LEAKED 💧

// FIX — one keyword:
class Base {
public:
    virtual ~Base() { cout << "~Base\n"; }   // ✅
};
// now: "~Derived" then "~Base" — correct, reverse order
🏭 Industry framing: This single missing keyword is one of the most common real leak sources in C++ codebases. Any base class you'd delete through a base pointer needs it. Modern rule: give a polymorphic base either a public virtual destructor, or a protected non-virtual one (if deletion through the base isn't allowed).
💡 Hook: ☠️ Non-virtual destructor = the demolition crew only tears down the ground floor and leaves the upper floors standing. Everything the derived class built stays in memory forever.
🎯 Say this: “Deleting a derived object through a base pointer with a non-virtual destructor is undefined behaviour — typically the derived destructor is skipped and its resources leak. Any polymorphic base needs a virtual destructor.”

9 Object slicing 🔪

Definition: When a derived object is assigned or passed by value to a base-type variable, the derived part is “sliced off” — only the base subobject is copied. The object loses its derived data and its polymorphic behaviour.
class Base { public: virtual void id() { cout << "Base\n"; } };
class Derived : public Base {
    int extra = 42;
public: void id() override { cout << "Derived\n"; }
};

void byValue(Base b)  { b.id(); }    // 🔪 SLICED → "Base"
void byRef(Base& b)   { b.id(); }    // ✅ polymorphic → "Derived"
void byPtr(Base* b)   { b->id(); }   // ✅ polymorphic → "Derived"

Derived d;
byValue(d);   // "Base"    ← the trap
byRef(d);     // "Derived"
byPtr(&d);    // "Derived"

Base b = d;   // 🔪 sliced: `extra` is gone, vptr is Base's
⚠️ Why it's dangerous: it compiles without a warning. vector<Base> holding derived objects slices every single one. Use vector<unique_ptr<Base>> instead.
💡 Hook: 🔪 Putting a tall person into a short box — you keep the part that fits and cut off the rest. And nobody warns you.
🎯 Say this: “Slicing happens when you copy a derived object into a base-typed variable by value — the derived portion is discarded and polymorphism is lost. The fix is to always handle polymorphic objects through references or pointers, ideally smart pointers.”

10 Abstract classes & interfaces 📐

Pure virtual function: virtual void draw() = 0; — declared but not (necessarily) defined; derived classes must override it.
Abstract class: any class with ≥1 pure virtual function. Cannot be instantiated — only inherited from.
Interface: (a convention, not a C++ keyword) an abstract class with only pure virtuals and no data.
class PaymentMethod {                        // abstract — an interface
public:
    virtual void pay(double amt) = 0;         // pure virtual
    virtual string name() const = 0;
    virtual ~PaymentMethod() = default;      // ✅ virtual dtor
};

class UPI : public PaymentMethod {
public:
    void pay(double amt) override { /* UPI flow */ }
    string name() const override { return "UPI"; }
};
class Card : public PaymentMethod { /* ...card flow... */ };

// PaymentMethod p;              // ❌ error: abstract, cannot instantiate
PaymentMethod* p = new UPI();      // ✅ pointer to abstract base is fine
p->pay(500);                     // runs UPI::pay
  • A derived class that doesn't override every pure virtual is itself abstract.
  • A pure virtual function can have a body — useful as a shared default that derived classes call explicitly.
  • C++ has no interface keyword — the pattern is an all-pure-virtual abstract class.
🏭 Industry framing: This is the plugin/strategy pattern, and it's the single most useful OOP idea in production. Checkout code depends on PaymentMethod*. Adding crypto next quarter = one new class, zero changes to checkout. That's Dependency Inversion + Open/Closed in three lines.
💡 Hook: 📐 Abstract class = a job description. You can't hire “a Job Description” — you hire a person who fulfils it.
🎯 Say this: “An abstract class defines a contract via pure virtual functions and can't be instantiated. I use it to program against interfaces rather than concrete types, so new implementations plug in without touching consumers.”

11 Shallow vs deep copy 💧

Shallow copy: copies member values — including pointer addresses. Two objects end up pointing at the same heap memory. This is what the compiler-generated copy constructor does.
Deep copy: allocates new memory and copies the pointed-to contents. Each object owns its own buffer.
class Buffer {
    int* data; int n;
public:
    Buffer(int n) : n(n) { data = new int[n]; }

    // DEEP copy constructor
    Buffer(const Buffer& o) : n(o.n) {
        data = new int[n];                    // ✅ own memory
        std::copy(o.data, o.data + n, data);   // ✅ copy contents
    }
    ~Buffer() { delete[] data; }
};
⚠️ The failure chain: default shallow copy → two objects share one pointer → first destructor frees it → second object's pointer is now dangling → second destructor frees it again → double free, heap corruption, crash.
💡 Hook: Shallow = photocopying a house key 🔑 — two keys, one house. Deep = building a second house 🏠🏠.

12 Rule of Three / Five / Zero ⭐

Rule of Three: if you need any one of: destructor, copy constructor, copy assignment operator — you almost certainly need all three. (Because needing one means you manage a resource manually.)
Rule of Five (C++11): add the move constructor and move assignment operator.
Rule of Zero: ✅ the modern answer — design so you need none of them, by holding resources in types that already manage themselves (std::vector, std::string, unique_ptr).
The FiveSignature
Destructor~T();
Copy constructorT(const T&);
Copy assignmentT& operator=(const T&);
Move constructorT(T&&) noexcept;
Move assignmentT& operator=(T&&) noexcept;
// ❌ Rule of Three violated — has a destructor, no copy ops → shallow copy → double free
class Bad { int* p; public: Bad(){p=new int;} ~Bad(){delete p;} };

// ✅ Rule of ZERO — no destructor, no copy ops, no bugs. vector handles everything.
class Good { std::vector<int> data; };   // copy, move, destroy all correct for free

Copy vs Move — in one line

  • Copy = duplicate the resource (expensive). Move = steal the pointer and null out the source (cheap).
  • Move is used when the source is a temporary/rvalue or explicitly std::moved — because nobody will look at it again.
💡 Hook: Copy = photocopying a document 📄📄 (slow, two copies). Move = handing the original over 🤝 (instant, you no longer have it).
🏭 Industry framing: Saying “I aim for the Rule of Zero” is the strongest signal in this whole page. It says: I don't hand-manage memory, I compose RAII types, so copy/move/destroy are correct by construction. That's how modern C++ is actually written.
🎯 Say this: “If a class manages a resource it needs all five; but I'd rather write none — the Rule of Zero. Wrap the resource in a unique_ptr or vector, and the compiler-generated operations are already correct and exception-safe.”

🔥 Most-asked questions (Part 2 scope)

These are the ones that actually decide the interview. Answer out loud first.

What is a virtual function and how does it work internally?
A member function declared virtual in the base and overridden in a derived class, so calls dispatch on the object's dynamic type. Internally: each polymorphic class has a vtable (an array of function pointers), and each object carries a hidden vptr to its class's vtable. p->draw() becomes: dereference vptr, index the vtable, call. One indirection; the vptr is set up by the constructor.
Hook: vtable = the restaurant's menu (per class), vptr = the menu in your hand (per object).
Why can't a constructor be virtual?
Virtual dispatch needs the vptr, and the vptr is initialised by the constructor itself. At construction time the object's dynamic type doesn't exist yet, so there's nothing to dispatch on. Related question they may follow with: can a destructor be virtual? Yes — and it usually must be, because by then the object is fully formed.
Why must a base class destructor be virtual? What happens if it isn't?
If you delete a derived object through a base pointer and the destructor isn't virtual, the behaviour is undefined — in practice only ~Base() runs, the derived destructor is skipped, and everything the derived class allocated leaks. Rule: any class intended as a polymorphic base needs a public virtual destructor (or a protected non-virtual one if deletion through the base is disallowed).
Say: “It's one keyword between correct code and a silent leak.”
What happens if you call a virtual function inside a constructor?
It does not dispatch to the derived override. During base construction the object is a Base — the vptr still points at the base's vtable, because the derived part isn't constructed yet. So you get the base version, which surprises people badly. Same applies in destructors, in reverse. Never rely on virtual dispatch in constructors or destructors.
Difference between overloading and overriding?
Overloading: same name, different parameters, same scope, resolved at compile time, no virtual needed. Overriding: same name and identical signature, base vs derived, requires virtual, resolved at runtime. Bonus points: mention name hiding — a same-named member in the derived class hides the entire base overload set, fixed with using Base::f;.
What is object slicing?
Copying a derived object into a base-typed variable by value — the derived portion is discarded, keeping only the base subobject. The object loses its extra data and its polymorphic behaviour (the copy gets the base's vptr). It compiles silently with no warning. Avoid by passing/storing polymorphic objects via references or pointers (vector<unique_ptr<Base>>, not vector<Base>).
Hook: Forcing a tall person into a short box — you keep what fits.
Compile-time vs runtime polymorphism — with mechanisms.
Compile-time (static/early binding): function overloading, operator overloading, templates. Resolved by the compiler via signature matching; zero runtime cost and inlinable. Runtime (dynamic/late binding): virtual functions accessed through a base pointer or reference; resolved via vptr→vtable lookup; costs one indirection and typically prevents inlining. Use runtime polymorphism when the set of types isn't known at the call site.
What is the diamond problem and how does C++ solve it?
With multiple inheritance, if B and C both derive from A and D derives from B and C, D contains two separate A subobjects — so d.x is ambiguous and there's duplicated state. C++ solves it with virtual inheritance (class B : virtual public A), which makes B and C share a single A subobject. Cost: extra indirection, and the most-derived class (D) becomes responsible for constructing the virtual base. Java avoids the problem by disallowing multiple class inheritance.
Shallow vs deep copy — and why does it crash?
Shallow copy (what the compiler generates) copies the pointer value, so two objects reference the same heap block. Deep copy allocates new memory and copies the contents. The crash chain: first destructor frees the block → the second object's pointer is dangling → second destructor frees it again → double free and heap corruption. Fix: write a deep copy constructor and copy assignment — or better, hold the resource in a vector/unique_ptr and write none.
What is the Rule of Three / Five / Zero?
Three: if you need a destructor, copy constructor, or copy assignment, you need all three — needing one implies manual resource management. Five (C++11): add move constructor and move assignment. Zero: the modern goal — design classes that need none by holding resources in self-managing types. Then the compiler-generated operations are automatically correct.
Say: “I aim for the Rule of Zero — let unique_ptr and vector do the managing.”
Copy vs move semantics — what's actually different?
Copy duplicates the resource — a new allocation plus a content copy. Move transfers ownership — steal the pointer, null out the source, no allocation. Move applies when the source is an rvalue (a temporary) or explicitly std::moved, i.e. when nobody will inspect the source again. Mark move operations noexcept, or std::vector will fall back to copying during reallocation for exception safety.
Abstract class vs interface in C++?
An abstract class has ≥1 pure virtual function (= 0) and cannot be instantiated; it may also have data members and implemented methods. An interface isn't a C++ keyword — it's the convention of an abstract class containing only pure virtuals and no state. Note: a pure virtual function may still have a definition, which derived classes can call explicitly as a shared default.
Can you instantiate an abstract class? Can you have a pointer to one?
You cannot instantiate it — Shape s; is an error. You absolutely can have a Shape* or Shape&, and that's the entire point: it's how you hold any concrete subtype behind one contract and get runtime polymorphism.
Is inheritance always good? (the design question)
No — prefer composition over inheritance. Inheritance couples the derived class to the base's implementation, so base changes ripple; deep hierarchies get rigid; and behaviour can't be swapped at runtime. Use inheritance for a genuine is-a relationship and for defining interfaces; use composition (has-a) for reuse. A Car has an Engine — it doesn't inherit from one.
Bringing this up unprompted is a strong senior signal.
Why does `sizeof` an object grow when you add a virtual function?
Because the object gains a hidden vptr — typically 8 bytes on a 64-bit build. Note the vtable itself is per class, not per object; only the pointer lives in each object. It's a neat question because it proves you understand the mechanism rather than the slogan.
What does `override` do, and why use it?
It tells the compiler “this is intended to override a base virtual”. If the signature doesn't actually match one, you get a compile error instead of silently creating an unrelated new function that never gets called. It's free bug prevention — a subtly wrong signature (a missing const, say) is otherwise a nightmare to spot. Related: final prevents any further overriding.
Does C++ support multiple inheritance? Does Java? Why the difference?
C++ does; Java does not (for classes) but allows multiple interfaces. The difference is the diamond problem: C++ accepts the complexity and hands you virtual inheritance to manage it; Java chose to eliminate the ambiguity by design, since interfaces carry no state to duplicate.
Three things that can't be virtual?
Constructors (no vptr yet), static member functions (no object, no this), and friend functions (not members at all). Also worth knowing: virtual-ness is inherited — once a function is virtual in the base, it stays virtual in every derived class even if you omit the keyword.

🎤 Walk-in checklist — say these unprompted and you sound senior

  • “Prefer composition over inheritance” — inheritance for interfaces, composition for reuse
  • “I aim for the Rule of Zero” — let RAII types manage resources
  • “Any polymorphic base needs a virtual destructor”
  • “I always mark overrides override” — turns silent bugs into compile errors
  • “Store polymorphic objects as vector<unique_ptr<Base>>” — no slicing, no leaks
  • Connect a concept to a real system (payments, plugins, locks) — theory + application beats theory
