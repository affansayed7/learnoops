1 Operator overloading ➕

Definition: Giving an existing operator (+, ==, <<…) a user-defined meaning for your own types. It's compile-time polymorphism — just a function with a funny name.

a + b is literally sugar for a.operator+(b) or operator+(a, b). Nothing magic.

Member vs Friend — the decision that gets asked

Member functionFriend / free function
Left operandMust be your class (it's this)Can be anything
ParamsOne fewer (left is implicit)All operands explicit
Use for= [] () -> (must be members)<< >>, symmetric ops
class Complex {
    double re, im;
public:
    Complex(double r = 0, double i = 0) : re(r), im(i) {}

    // MEMBER: left operand is *this
    Complex operator+(const Complex& o) const {
        return Complex(re + o.re, im + o.im);
    }
    bool operator==(const Complex& o) const {
        return re == o.re && im == o.im;
    }

    // FRIEND: left operand is ostream — CAN'T be a member!
    friend ostream& operator<<(ostream& os, const Complex& c) {
        return os << c.re << " + " << c.im << "i";
    }
};

Complex a(1,2), b(3,4);
cout << a + b;        // "4 + 6i"
⚠️ Why << can't be a member: the left operand would have to be this — but the left operand is cout, an ostream. You don't own ostream, so you can't add members to it. Hence a friend free function. This is THE reason friends exist — say it exactly like that.

Rules & limits

  • Cannot overload: .  ::  ?:  sizeof  .* — memorise these five.
  • Cannot invent new operators (**), change arity, or change precedence.
  • At least one operand must be a user-defined type — you can't redefine int + int.
  • Return by value for +; return by reference for =, +=, << (enables chaining).

Copy assignment — the one they check

Buffer& operator=(const Buffer& o) {
    if (this == &o) return *this;   // ① self-assignment guard!
    delete[] data;                   // ② free old
    n = o.n;
    data = new int[n];               // ③ deep copy
    std::copy(o.data, o.data + n, data);
    return *this;                    // ④ return ref → chaining a = b = c
}
⚠️ Forget the self-assignment check and x = x; deletes the data then copies from the freed buffer. Interviewers look for this line specifically.
💡 Hook: a + b = “a.operator+(b)” in a costume 🎭. Once you see operators as plain functions, everything clicks.
🎯 Say this: “Operator overloading is compile-time polymorphism. I use members when the left operand is my type, and free/friend functions when it isn't — like operator<<, where the left operand is a stream. And I always guard operator= against self-assignment.”

2 Templates & generic programming 🧬

Definition: Blueprints for generating code at compile time. One template → the compiler stamps out a separate concrete class/function for each type used. This is compile-time polymorphism.
template<typename T>
class Stack {
    std::vector<T> items;
public:
    void push(const T& x) { items.push_back(x); }
    T pop() { T t = items.back(); items.pop_back(); return t; }
    bool empty() const { return items.empty(); }
};

Stack<int> si;        // compiler generates Stack_int
Stack<string> ss;     // and a separate Stack_string

Templates vs Virtual functions — the real comparison

TemplatesVirtual functions
BindingCompile timeRuntime
CostZero — fully inlinableOne indirection
Types knownAt build timeCan arrive later (plugins)
Code sizeGrows (one copy per type)One copy
Needs inheritance?No — duck typingYes — common base
💡 Hook: Template = a cookie cutter for cookie cutters 🍪✂️✂️ — it stamps out classes, not objects.
🏭 Industry framing: The whole STL is templates — vector<T>, map<K,V>, sort. That's why sort on a vector<int> matches hand-written C speed: it's generated and inlined for int, no runtime dispatch. Java's generics erase to Object; C++ templates don't — hence the performance difference.
🎯 Say this: “Templates give compile-time polymorphism with zero runtime cost, at the price of code bloat and build time. Virtual functions give runtime flexibility for one indirection. I pick templates when the types are known at compile time, virtual when they aren't — like a plugin system.”

3 Smart pointers 🧠 — the modern C++ answer

Definition: RAII wrappers around raw pointers that own the memory and free it automatically in their destructor. This is the Rule of Zero in practice.
TypeOwnershipCostUse when
unique_ptr<T>Exclusive — one owner, movable, not copyableZero overheadDefault choice. 90% of cases
shared_ptr<T>Shared — reference counted, freed at count 0Atomic refcount + control blockGenuinely shared ownership
weak_ptr<T>None — observes a shared_ptr without owningSmallBreaking cycles; caches
// ❌ old way — leaks if anything throws between new and delete
Shape* s = new Circle();
delete s;

// ✅ modern — freed automatically, exception-safe
auto s = std::make_unique<Circle>();

// ✅ polymorphic container — no slicing, no leaks
std::vector<std::unique_ptr<Shape>> shapes;
shapes.push_back(std::make_unique<Circle>());
shapes.push_back(std::make_unique<Square>());
for (auto& sh : shapes) sh->draw();   // virtual dispatch ✅

The circular reference problem — why weak_ptr exists

⚠️ Always use make_unique / make_shared, not new. Reasons: exception safety, and make_shared allocates the object + control block in one allocation instead of two.
💡 Hook: unique_ptr = the only key to a flat 🔑 (you can hand it over, not photocopy it). shared_ptr = flatmates 👥 — last one out turns off the lights. weak_ptr = a visitor 👀 who can look but doesn't pay rent, so they never stop the lease ending.
🎯 Say this: “I default to unique_ptr — zero overhead and it expresses exclusive ownership. shared_ptr only when ownership is genuinely shared, since the atomic refcount isn't free. weak_ptr to break cycles, because reference counting can't collect them.”

4 SOLID principles 🏛️

Five design principles. Asked directly (“explain SOLID”) and indirectly (“how would you design X?”). Learn the one-liners cold.

S

Single Responsibility

A class should have one reason to change — one job.

❌ Invoice that calculates totals and prints PDFs and emails customers → ✅ split into Invoice, InvoiceRenderer, InvoiceMailer.

O

Open/Closed

Open for extension, closed for modification. Add features by adding code, not editing working code.

❌ a switch on payment type you edit every quarter → ✅ a PaymentMethod interface; add a class, touch nothing.

L

Liskov Substitution

A derived object must be usable anywhere its base is expected, without surprises.

❌ the classic: Square : Rectangle. setWidth(5) on a Square also changes height — code written against Rectangle breaks. They're not substitutable.

I

Interface Segregation

Many small focused interfaces beat one fat one. Don't force a class to implement methods it doesn't need.

❌ IMachine{print,scan,fax} forcing a simple printer to stub out fax() → ✅ IPrinter, IScanner, IFax.

D

Dependency Inversion

Depend on abstractions, not concretions. High-level policy shouldn't import low-level details.

❌ OrderService that news a MySQLDatabase → ✅ it takes an IDatabase&. Now you can inject a mock in tests.

🏭 Industry framing: The honest reason SOLID matters: testability. Dependency Inversion is what makes unit testing possible — if OrderService hard-codes a real database, you can't test it without one. Mentioning testing shows you've shipped software, not just read about it.
💡 Hook: Single · Open · Liskov · Interface · Dependency. If you blank on one, the L is Liskov — remember the square/rectangle story and you'll reconstruct it.

5 Design patterns — the four that get asked 🧩

① Singleton — exactly one instance

class Logger {
    Logger() = default;                     // private ctor
public:
    Logger(const Logger&) = delete;           // no copying
    Logger& operator=(const Logger&) = delete;

    static Logger& get() {
        static Logger instance;             // thread-safe since C++11
        return instance;
    }
    void log(const string& m) { cout << m; }
};
Logger::get().log("started");
⚠️ Bonus points: that's the Meyers Singleton. The local static is initialised lazily and thread-safely (guaranteed by C++11). Also mention the criticism: singletons are global state — they hurt testability, which is why many teams avoid them.

② Factory — create without naming the concrete class

static std::unique_ptr<Shape> create(const string& type) {
    if (type == "circle") return std::make_unique<Circle>();
    if (type == "square") return std::make_unique<Square>();
    return nullptr;
}

Caller gets a Shape without knowing which subclass exists. Object creation lives in one place.

③ Strategy — swap an algorithm at runtime

class Sorter {
    std::unique_ptr<SortStrategy> strategy;      // composition!
public:
    void setStrategy(std::unique_ptr<SortStrategy> s) { strategy = std::move(s); }
    void run(vector<int>& v) { strategy->sort(v); }   // behaviour is swappable
};

This is “prefer composition over inheritance” made concrete — behaviour is a member you can replace, not a base class you're stuck with.

④ Observer — publish/subscribe

class Subject {
    vector<Observer*> observers;
public:
    void attach(Observer* o) { observers.push_back(o); }
    void notify() { for (auto* o : observers) o->update(); }
};

One-to-many: when the subject changes, all subscribers hear about it. Every UI event system and message bus you've used.

🎯 Say this: “Patterns are named solutions to recurring design problems — a shared vocabulary. I use Strategy and Factory routinely; I'm cautious with Singleton because it's global state that makes testing harder.”

6 const correctness & explicit

class Account {
    double balance;
public:
    explicit Account(double b) : balance(b) {}   // no implicit conversion

    double get() const { return balance; }        // ✅ won't modify object
    void deposit(double a) { balance += a; }       // non-const
};

const Account a(500);
a.get();        // ✅ const method on const object
// a.deposit(1); // ❌ error — non-const method on const object
  • const after the function = “I won't modify *this”. Only const methods are callable on const objects.
  • Read pointers right to left: const int* p = pointer to const int (data locked) · int* const p = const pointer (pointer locked) · const int* const p = both.
  • explicit blocks implicit conversions. Without it, Account a = 500; silently compiles — a number becoming an Account. Rule: mark single-argument constructors explicit.
  • mutable lets one member change even inside a const method (legit use: a cache or a mutex).
🎯 Say this: “const correctness is compiler-enforced documentation. It's easiest to apply from the start — retrofitting it into a codebase is painful, because const propagates.”

7 The four casts & dynamic_cast 🎯

CastPurposeChecked?
static_castRelated types, upcasts, numeric conversionsCompile time only
dynamic_castSafe downcast in a polymorphic hierarchy✓ Runtime (RTTI)
const_castAdd/remove constNo
reinterpret_castBit-level reinterpretation✗ Dangerous
Base* b = new Derived();

Derived* d = dynamic_cast<Derived*>(b);
if (d) { /* ✅ it really was a Derived */ }
else   { /* ✅ returns nullptr on failure — SAFE */ }

Derived* d2 = static_cast<Derived*>(b);   // ⚠️ no check — UB if wrong
  • dynamic_cast needs a polymorphic type (≥1 virtual function) — it reads RTTI via the vptr.
  • On pointers it returns nullptr on failure; on references it throws std::bad_cast.
  • C-style casts are banned in modern code: they silently pick whichever cast fits, and they're ungreppable.
⚠️ Design smell: reaching for dynamic_cast often means a missing virtual function. If you're asking “what type is this?”, the object should probably just do the thing polymorphically instead.

8 Exceptions & safety 🛡️

try {
    process();
} catch (const std::runtime_error& e) {   // ✅ catch by const ref
    cerr << e.what();
} catch (...) { /* catch-all */ }
  • Catch by const reference — catching by value slices the exception object (Part 2's slicing, striking again 🔪).
  • Never let an exception escape a destructor — during stack unwinding that calls std::terminate. Destructors are implicitly noexcept in C++11.
  • Order catch blocks derived → base; the first match wins, so a base-first order swallows everything.
  • RAII is what makes exceptions safe — stack unwinding runs destructors, so resources release themselves. Raw new/delete between a throw and a catch = leak.
💡 The three guarantees: basic (no leaks, valid state) · strong (commit-or-rollback — the operation either fully succeeds or changes nothing) · nothrow (noexcept — never fails).
🎯 Say this: “Exception safety and RAII are the same conversation. If every resource is owned by an object, stack unwinding cleans up automatically and I don't need finally.”

🔥 Most-asked questions (Part 3 scope)

Answer out loud first — recognition isn't recall.

Why must `operator<<` be a friend/free function and not a member?
Because for a member operator, the left operand must be the class itself (it becomes this). In cout << obj the left operand is std::ostream — a type you don't own and can't add members to. So it must be a free function taking (ostream&, const T&), and it's declared a friend if it needs private access. Return ostream& to allow chaining.
Say: “This is the canonical legitimate use of friend.”
Which operators cannot be overloaded?
Five: . (member access), :: (scope resolution), ?: (ternary), sizeof, and .* (pointer-to-member). Also: you can't invent new operators, change arity, or change precedence/associativity. At least one operand must be a user-defined type.
What's the one line people forget in `operator=`?
The self-assignment guard: if (this == &other) return *this;. Without it, x = x; deletes the buffer and then copies from the freed memory — undefined behaviour. Also return *this by reference so a = b = c; chains. (The elegant alternative worth naming: the copy-and-swap idiom, which is self-assignment-safe and exception-safe by construction.)
unique_ptr vs shared_ptr — when do you use each?
unique_ptr is exclusive ownership: movable, not copyable, zero overhead versus a raw pointer. It's the default. shared_ptr is shared ownership via an atomic reference count and a separate control block — real cost, so only use it when ownership is genuinely shared and the last owner is unknown. Rule of thumb: reach for unique_ptr first and only upgrade if you must.
What problem does weak_ptr solve?
Circular references. Two shared_ptrs pointing at each other keep both counts at 1 forever — the memory never frees, because reference counting can't collect cycles. A weak_ptr observes without incrementing the count, breaking the cycle. To use it you call lock(), which returns a shared_ptr if the object still exists or null if it's gone. Also used for caches.
Hook: a visitor who doesn't pay rent, so they can't stop the lease ending.
Why prefer make_unique over new?
Exception safety and clarity — with make_unique there's no window where a raw pointer exists unowned. And make_shared specifically allocates the object and its control block in a single allocation instead of two, which is faster and more cache-friendly. Plus you never write delete, so you can't forget it.
Templates vs virtual functions — how do you choose?
Templates: compile-time, zero runtime cost, fully inlinable, no inheritance needed (duck typing) — but code bloat and slower builds, and all types must be known at compile time. Virtual: runtime dispatch for one indirection, single code copy, and types can arrive later (plugins, dynamic libraries). Choose templates when types are known at build time; virtual when they're not.
Explain SOLID.
Single Responsibility — one reason to change. Open/Closed — open to extension, closed to modification. Liskov Substitution — a derived object must work anywhere its base does, without surprises. Interface Segregation — many small interfaces over one fat one. Dependency Inversion — depend on abstractions, not concretions.
Add this: “The practical payoff is testability — Dependency Inversion is what lets me inject a mock instead of a real database.”
Give a concrete Liskov violation.
The classic: Square inheriting from Rectangle. Mathematically a square is a rectangle, so it feels right. But rect.setWidth(5) on a Square must also change the height to stay square — so any code written against Rectangle ("set width to 5, height stays 4, area is 20") breaks silently. They're not behaviourally substitutable, so the inheritance is wrong even though the "is-a" sentence sounds true. The lesson: is-a is about behaviour, not vocabulary.
How do you implement a thread-safe Singleton in C++?
The Meyers Singleton: a function-local static instance returned by reference, with the constructor private and copy/assignment = deleted. Since C++11 the standard guarantees function-local static initialisation is thread-safe and lazy, so no manual locking is needed. Worth adding the caveat: singletons are global state and hurt testability — many teams prefer dependency injection.
What does `explicit` do and why does it matter?
It blocks implicit conversions through a constructor. Without it, a single-argument constructor doubles as a conversion: Account a = 500; compiles, silently turning a number into an Account, and functions taking Account accept raw doubles. That's a bug factory. Rule: mark single-argument constructors explicit unless you deliberately want the conversion.
static_cast vs dynamic_cast?
static_cast is resolved at compile time with no runtime check — fine for upcasts and numeric conversions, but a wrong downcast is undefined behaviour. dynamic_cast performs a runtime check using RTTI (via the vptr), so it requires a polymorphic type; it returns nullptr for a failed pointer cast or throws std::bad_cast for a reference cast. Use dynamic_cast when a downcast might legitimately fail — but frequent need for it usually signals a missing virtual function.
Why catch exceptions by const reference?
Catching by value slices the exception — if you catch std::exception by value but a std::runtime_error was thrown, the derived part is cut off and what() loses its message. Catching by reference preserves the dynamic type and polymorphism, and avoids a copy. const because you're inspecting, not modifying. Also order catch blocks derived → base, since the first match wins.
Why must destructors not throw?
If an exception is already propagating and a destructor throws during stack unwinding, you have two active exceptions and the runtime calls std::terminate — instant crash, no recovery. That's why destructors are implicitly noexcept in C++11. If cleanup can genuinely fail, swallow it or expose a separate close() that callers can check.
What are the exception safety guarantees?
Three levels: basic — no leaks, object remains valid but possibly changed; strong — commit-or-rollback, the operation either fully succeeds or leaves everything untouched (vector::push_back gives this); nothrow/noexcept — cannot fail (swap, destructors, move operations should be). RAII is how you get the basic guarantee for free, and copy-and-swap is a standard route to the strong one.
