Encapsulation & Abstraction — Deep Dive 🔒🎛️

Note 02 gave you the one-liners. This note gives you the design judgment — invariants, real code, and the distinction interviewers actually probe.

1 Encapsulation is not "just add getters and setters"

Here's a class that is technically encapsulated — private data, public methods — and is still a bad design:

class BankAccount {
    double balance;
public:
    void setBalance(double b) { balance = b; }   // accepts ANY value, no checks
    double getBalance() { return balance; }
};

BankAccount acc;
acc.setBalance(-999999);   // ✅ "compiles and runs" — but the account is now broken
  • The data is technically private. But the setter does zero validation — it's a pass-through, functionally identical to making balance public.
  • This pattern is sometimes called an anemic domain model: a class that's just a bag of getters/setters with no actual behavior or protection. It's a genuine design smell interviewers look for.
  • Real encapsulation isn't about the keyword private — it's about protecting invariants.
⚠️ The interview trap: if asked to "spot the encapsulation issue" in a code sample, don't just check for public data members — check whether the setters actually enforce anything.

2 Invariants — the real thing encapsulation protects

Invariant: a condition that must always be true for an object, across its entire lifetime — no matter which method was just called.
  • A BankAccount's invariant: balance can never go negative.
  • A Date's invariant: month is always 1–12, day is always valid for that month.
  • A sorted vector wrapper's invariant: the elements are always in order.
  • Encapsulation's actual job: make it impossible to reach a state that violates the invariant, by routing every mutation through code that checks it.
class BankAccount {
    double balance;
public:
    BankAccount(double initial) : balance(initial >= 0 ? initial : 0) {}  // invariant enforced at birth

    bool withdraw(double amt) {
        if (amt < 0 || amt > balance) return false;  // ← the checkpoint
        balance -= amt;
        return true;
    }
    void deposit(double amt) {
        if (amt > 0) balance += amt;               // ← another checkpoint
    }
    double getBalance() const { return balance; }  // read-only, can't break anything
};
💡 Memory hook: An invariant is a promise the object makes about itself, forever. Encapsulation is the bouncer that makes sure no code path can ever break that promise.
🎯 Interview line: "Encapsulation's real purpose is protecting class invariants — conditions that must hold for the object to be valid — by ensuring every mutation is routed through code that can enforce them."

3 How const reinforces encapsulation

class Account {
    double balance;
public:
    double getBalance() const { return balance; }   // promises: won't touch invariant
    void deposit(double amt) { balance += amt; }       // can mutate — NOT const
};

const Account a(100);
a.getBalance();     // ✅ read-only method on a const object — fine
// a.deposit(50);   // ❌ compile error: deposit is non-const
  • A const member function is a compiler-enforced promise not to modify the object's state.
  • This means a const Account& parameter genuinely can't have its invariant broken by whoever receives it — the compiler polices it, not just convention.
💡 Hook: const methods are the "look but don't touch" section of your class's interface.

4 Bonus precision: encapsulation vs information hiding

These get used interchangeably in casual conversation, but there's a real distinction worth having in your pocket:

Information HidingEncapsulation
A general design principle (Parnas, 1972) — hide decisions likely to change behind a stable interfaceThe specific OOP mechanism — classes + access specifiers — commonly used to achieve it
Applies to any paradigm — even a C module can hide its internal struct layout via an opaque pointerApplies specifically to classes and objects
A goalA tool that achieves the goal
🎯 If asked directly: "Information hiding is the broader design principle of hiding implementation details behind a stable interface — it predates OOP. Encapsulation is how object-oriented languages implement that principle, using access specifiers to physically enforce the hiding." Most interviewers will accept the simpler one-liner from Note 02, but this shows depth if pushed.

5 Abstraction — hiding complexity, with real code

A stack that hides its internal representation completely:

class Stack {
    std::vector<int> data;         // implementation detail — could be an array, a list, anything
public:
    void push(int x) { data.push_back(x); }
    void pop()          { data.pop_back(); }
    int  top() const   { return data.back(); }
    bool empty() const { return data.empty(); }
};
  • The caller knows push, pop, top, empty — that's the essential interface.
  • The caller has no idea it's backed by a vector. You could swap it for a linked list tomorrow and every caller keeps working unchanged.
  • This is abstraction's actual payoff: implementation is free to change as long as the interface's behavior doesn't.

Abstraction's formal C++ tool: the abstract class (preview)

class Shape {
public:
    virtual double area() const = 0;    // pure virtual — the essential interface
    virtual ~Shape() = default;
};
class Circle : public Shape {
    double r;
public:
    Circle(double r) : r(r) {}
    double area() const override { return 3.14159 * r * r; }
};
⚠️ This is a preview only. Abstract classes, pure virtual functions, and why Shape s; won't compile get their full treatment in the upcoming Polymorphism note — they need virtual functions explained first.
💡 Hook: Abstraction is a car's pedal 🚗 — press to go, fuel injection isn't your problem. Encapsulation is the locked hood 🔒 stopping you from yanking the wires yourself even if you wanted to.

They usually show up together, but they answer different questions — encapsulation is about access, abstraction is about design."
